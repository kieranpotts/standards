= Runtimes

This section covers best practices for targeting specific versions of Node, web
browsers, and other JavaScript runtime environments.

== Node

Node's https://nodejs.org/en/about/releases/[release strategy] can be confusing,
but in short: at any point in time Node has one "current" major release, one
"active" LTS (long-term support) release, and at least two older LTS releases
under "maintenance". For example, in February 2022 the supported major versions
were v17 (current), v16 (active LTS), v14 (maintenance), and v12 (maintenance);
by February 2023 they were v19 (current), v18 (active LTS), v16 (maintenance),
and v14 (maintenance).

The "current" versions are short-lived: Node's current release gets a major
version bump every six months, and odd-numbered major releases (11, 13, 15,
etc.) stop being supported as soon as they lose "current" status, just six months
after release. The "current" and odd-numbered releases are often too volatile
to make support worthwhile. Node's own recommendation is that production
applications should use only active LTS or maintenance LTS releases – the
even-numbered releases.

We can therefore concern ourselves mostly with the even-numbered releases (10,
12, 14, 16, 18, etc.). These versions are actively maintained for two-and-a-half
years from their initial release. LTS for each even-numbered major version
begins at a specific release:

* Node v10 ("Dubnium") – LTS starts at https://github.com/nodejs/node/blob/master/doc/changelogs/CHANGELOG_V10.md#10.13.0[10.13.0].

* Node v12 ("Erbium") – LTS starts at https://github.com/nodejs/node/blob/master/doc/changelogs/CHANGELOG_V12.md#12.13.0[12.13.0].

* Node v14 ("Fermium") – LTS starts at https://github.com/nodejs/node/blob/master/doc/changelogs/CHANGELOG_V14.md#14.15.0[14.15.0].

* Node v16 ("Gallium") – LTS starts at https://github.com/nodejs/node/blob/master/doc/changelogs/CHANGELOG_V16.md#16.13.0[16.13.0].

* Node v18 ("Hydrogen") – LTS starts at https://github.com/nodejs/node/blob/master/doc/changelogs/CHANGELOG_V18.md#18.12.0[18.12.0].

It is these initial LTS releases of each major version that SHOULD be our
baseline targets for support. The `engines` field in `package.json` specifies
which versions of Node a package or application is compatible with. For example,
as of May 2023 the supported versions were `^14.15.0` (maintenance),
`^16.13.0` (maintenance), and `^18.12.0` (active):

[source,json]
----
{
  "engines": {
    "node": "^14.15.0 || ^16.13.0 || ^18.12.0"
  }
}
----

It is common for open source JavaScript packages to adopt a "current + LTS"
policy that includes the odd-numbered current release. Such a policy MUST be
implemented only in special circumstances, where there is business justification
for targeting a short-lived major release:

[source,json]
----
{
  "engines": {
    "node": "^14.15.0 || ^16.13.0 || ^18.12.0 || ^19.0.0"
  }
}
----

=== Dropping support for Node versions

Dropping support for a major version of Node MUST happen in a major version bump
of our packages, per semantic-versioning principles. To give the major versions
of our packages the longest possible lifespans, we SHOULD NOT drop support for a
major version of Node just because its maintenance has been discontinued. Once a
major version of Node is supported, we SHOULD keep it as a target until there are
practical reasons that support must stop (for example, CI systems drop support,
preventing tests from running). Our actual list of supported Node versions is
therefore expected to grow over time:

[source,json]
----
{
  "engines": {
    "node": "^10.13.0 || ^12.13.0 || ^14.15.0 || ^16.13.0 || ^18.12.0"
  }
}
----

=== Other system software requirements

The `engines` field SHOULD also be used to declare other system software on which
the package depends, particularly in repository manifests to declare
dependencies on development tools such as Yarn and NPM:

[source,json]
----
{
  "engines": {
    "node": "^14.16.0",
    "yarn": "^1.22.0"
  }
}
----

=== Version number constraints

Use of the `^` character is the RECOMMENDED way to lock versions to a
particular major release of a dependency. `^10.13.0` means all minor and patch
releases from that version onwards (10.14.0, 10.15.0, 10.15.1, etc.) but not the
) but not the
next major version (11.x.x). See <<Dependency management>> for further guidance
on version number constraints.

=== Node built-in modules

Use the `node:` URL scheme to import Node built-in modules, to distinguish them
from vendor and local modules:

[source,javascript]
----
import fs from 'node:fs/promises'
----

This syntax is available from Node v12.20.0 and v14.13.1, and in `require()`
from Node v14.18.0 and v16.0.0.

== Web

All major web browsers now implement the standard JavaScript module system via
`<script type="module">`; the same ESM conventions apply on the web as on the
server (see <<Modules>>). Where the cost of many separate module requests
outweighs the benefit, modules MAY be bundled for delivery. A "cut-the-mustard"
progressive-enhancement strategy MAY be used to load JavaScript only in browsers
that meet baseline runtime requirements.
