= Model Context Protocol

Agents become useful when they can reach beyond the model – reading and writing files, querying databases, calling APIs, searching the web, and taking actions in external systems. The question is how those connections are made. Historically, each tool or data source required bespoke integration code written against a specific agent or harness.

The *Model Context Protocol (MCP)* is an open standard, introduced by Anthropic in late 2024, that addresses this. It defines a common protocol for how models and agents communicate with external tools and data sources, so that any compliant tool can be connected to any compliant agent without custom integration work.

MCP is a client-server protocol. An *MCP server* exposes a set of tools and resources; an *MCP client* – typically the agent or AI application – connects to one or more servers and uses their tools to fulfil tasks. A single agent can connect to many servers at once, giving it a large, composable action space. This makes MCP particularly relevant to the agentic workflows described in the previous chapter.

MCP is not the only proposal in this space – Google's A2A (Agent-to-Agent) and IBM/BeeAI's ACP (Agent Communication Protocol) are among the alternatives – and the area is still maturing. This chapter's guidance applies to MCP specifically, but the principles transfer to whatever integration standard a project adopts.

== Prefer open protocols over bespoke integration

When connecting an agent to external tools or data, it is RECOMMENDED to use an open protocol such as MCP rather than writing point-to-point integrations. The benefits are interoperability (any client works with any server), composability (one agent can draw on many servers), portability (integrations survive a change of harness or model), and reduced maintenance.

That said, the standards landscape is still early. Do not over-invest in any single protocol before it stabilizes. In practice, favor whatever your chosen harness supports natively, and prefer widely-adopted, actively-maintained servers over niche ones.

== Treat MCP servers as dependencies

An MCP server is third-party code that runs with access to your tools, data, and actions. It MUST be treated with the same scrutiny as any other software dependency (see also the model trust guidance in the security chapter).

* Prefer official or well-known servers. Review the source of community-provided servers before connecting them.
* Pin server versions where possible, and review changes before upgrading.
* Test unfamiliar servers in an isolated environment before introducing them to regular workflows.

A malicious or compromised server can exfiltrate any data the agent can reach and take any action its tools permit. The convenience of a large server ecosystem does not suspend normal supply-chain caution.

== Apply least privilege to server and tool access

An agent connected to many servers has a correspondingly large action space, and that action space defines the blast radius of any prompt injection or misbehavior. Apply the principle of least privilege at two levels:

* *Connection scope.* Connect only the servers and tools the current task actually needs. Do not connect servers "just in case."
* *Credential scope.* Scope each server's own credentials to the minimum required – for example, read-only database access where writes are not needed.

Review connected servers before starting a task, not only when first configuring the harness. A connection set appropriate for one task may be excessive for the next.

== Tool results are untrusted input

Data returned by an MCP server – web pages, file contents, API responses – is external content and a vector for indirect prompt injection (see the security chapter). The agent cannot reliably distinguish data it should process from instructions it should follow.

* Treat all tool output as data, not instructions.
* Prefer human confirmation before irreversible actions taken through MCP tools – file deletion, outbound messages, code execution, financial transactions – especially when the agent has just processed external content.
* Audit agent execution traces when tasks involve servers that fetch untrusted data.

== Transport and network exposure

MCP servers may run locally (communicating over stdio) or remotely (over HTTP). Local servers avoid network exposure entirely and SHOULD be preferred where the tool can run on the same host as the agent.

Remote servers MUST authenticate their clients and MUST use encrypted transport. An unauthenticated MCP server MUST NOT be exposed on a public network interface – the same network-exposure discipline that applies to local model servers (see the security chapter) applies here. Run servers only while they are needed rather than as always-on services.

== Mind the context cost of connected servers

Every connected server injects its tool definitions into the context window, consuming tokens and attention budget on *every* call – not just when its tools are used. Connecting many servers indiscriminately therefore degrades performance (through context rot) and increases cost (see the context engineering and cost optimization chapters).

Connect only the servers relevant to the task at hand, and design or select tools according to the tool-design principles in the context engineering chapter: small, focused, unambiguous, with no overlapping responsibilities.
