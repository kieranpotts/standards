= Agentic workflows

== Definitions

For decades, the developer's primary interface with the machine has been syntax — the precise grammar of programming languages. Agentic development is a change in emphasis. Developers now express what they want built — their intent — and trust intelligent systems to translate that intent into working software, rather than writing the syntax themselves. That intent is captured in artifacts — instructions, specifications, designs, plans — precise enough for an agent to act on and for a human, a script, or another agent to verify against. Trust in the result is not assumed. It is earned incrementally, through the guides and sensors described throughout this standard.

Agentic workflows are a distinct category of AI-assisted development. It is useful to distinguish them from other forms of AI-assisted development, and from traditional automation.

=== Agentic vs. AI-assisted development

While both agentic and AI-assisted development leverage Large Language Models (LLMs), they differ primarily in the locus of control and the nature of the interaction loop.

AI-assisted development is a model of *augmentation*. In this workflow, the human developer remains the primary driver of the process, using AI as a tool to perform specific sub-tasks—such as writing a function, explaining a code block, or generating a test case. The human manually manages the loop: prompt, review, apply, and iterate. The interaction between human and agent is synchronous.

Agentic workflows, by contrast, are a model of *delegation*. In this approach, the human shifts from being the primary implementer to being the supervisor. The agent is tasked with a high-level goal and is empowered to manage its own internal loop. It plans its own steps, executes them using available tools, observes the results, and corrects its course autonomously until the goal is achieved. The human intervenes not to perform the work, but to provide steering, constraints, and final approval. The interaction is more asynchronous in nature.

Different categories of tools are needed to support these two distinct workflows. *Code-first* workflows are supported by traditional development tools such as code editors and integrated development environments, augmented with built-in systems for code completion and other synchronous AI assistance. *Agent-first* workflows require a new category of "agent harness" tools via which you build applications by handing off tasks to AI agents to perform asynchronously. The primary interface is the agent chat window, rather than the code editor window. These tools shift the focus of the human work to defining the problem and reviewing the solution.

=== Agentic vs. Automation

It is also important to distinguish agentic workflows from traditional automation.

Automation consists of static, rules-based processes. A traditional automation script is deterministic. It follows a predefined sequence of "if-this-then-that" logic. If an automation script encounters a state it was not explicitly programmed to handle, it fails. Automation is ideal for repetitive, predictable tasks where the environment is stable.

Agentic workflows are dynamic and reasoning-based. Rather than following a rigid script, an agent uses a probabilistic model to reason through a problem. It can handle ambiguity, adapt to unexpected outputs from tools, and devise new strategies on the fly to overcome obstacles. While automation is about *execution of a known path*, agentic workflows are about *navigation toward a known goal*.

This distinction matters when choosing between approaches. Not every task that can be automated should be made agentic. Traditional automation — scripts, pipelines, scheduled jobs — is preferable when the task is deterministic, the environment is stable, and the failure modes are well understood. Reserve agentic approaches for tasks where the work involves genuine ambiguity, requires adaptive reasoning, or must recover from unexpected states. Agentic systems carry higher operational complexity and cost than equivalent automation scripts; that overhead is only justified where the model's reasoning capability is genuinely needed.

== Components of an agentic harness

An agent is more than just a model prompt. It is a system composed of three primary components that enable autonomous behavior:

* *The brain (reasoning engine)*: This is the LLM that powers the agent. The brain is responsible for planning, reasoning, and deciding which actions to take based on the current state and the final goal.

* *Memory*: Memory provides the context necessary for the agent to operate. This includes *short-term memory* (the current conversation window and session state) and *long-term memory* (persistent project knowledge, which includes things like the `AGENTS.md` and skills files).

* *Tools (capabilities)*: Tools are the interfaces the agent uses to interact with the external world. These may include file system access, shell execution, API calls, or specialized search utilities. Tools allow the agent to move from purely generative output to active implementation and verification.

== Agentic architectures

Depending on the complexity of the task, agentic systems can be organized into different architectural patterns.

=== Single-agent systems

The simplest architecture is the linear flow: `TASK → AGENT → SOLUTION`. In this model, a single agent is responsible for the entire lifecycle of the task—planning, execution, and verification. This is the recommended starting point for most tasks and is highly effective for well-defined goals with limited scope.

=== Multi-agent systems

For complex, large-scale projects, a hierarchical structure is often more effective: `TASK → SUPERVISOR AGENT → SUB-AGENTS → SOLUTION`.

In a multi-agent system, a *supervisor agent* acts as the project manager. It decomposes the high-level task into smaller, specialized sub-tasks and delegates them to *sub-agents*. These sub-agents may be specialized for specific roles (eg. a "Security Auditor" agent, a "Test Engineer" agent, or a "Documentation" agent). The supervisor then aggregates the results, ensures they are cohesive, and verifies the final outcome. This architecture models real-world organizational structures and reduces the likelihood of a single agent becoming overwhelmed by a massive context window or a too-broad objective.

== Resource optimization

To optimize for both quality and cost, agentic workflows should employ a tiered model strategy. Not every step of an agentic process requires the highest-reasoning capability available.

=== Model tiering

A hybrid approach using a mix of frontier (premium cloud) models and efficient (smaller or local) models is RECOMMENDED.

Use frontier models for the role of the *supervisor agent*. These models are best suited for complex planning, architectural decision-making, and high-level quality assurance.

Use smaller, faster, or locally-hosted models for the *sub-agents*, or for the execution of a pre-approved plan. Once a frontier model has defined a precise, step-by-step path, efficient models are often perfectly capable of implementing the code or performing routine checks at a fraction of the cost and latency.

By offloading the execution phase to efficient models while reserving the reasoning phase for frontier models, developers can maintain high output quality while significantly reducing token consumption and subscription costs.

== Guardrails

Guardrails are constraints that bound agent behavior, reducing the risk of unintended or harmful actions. They operate at several levels:

* *Permission constraints*: Explicit allow/deny lists that control which tools, shell commands, file paths, or network endpoints the agent may access. Configure these in the agent harness rather than relying on prompts — they are the most reliable form of guardrail because they are enforced by the runtime, not by the model's interpretation.

* *Behavioral instructions*: Rules embedded in system prompts or `AGENTS.md` that direct how the agent should approach tasks — for example, "create an explicit plan before making destructive changes" or "never commit directly to the main branch."

* *Validation gates*: Checkpoints at which the agent must verify a condition before proceeding — for example, running a test suite before committing code, or requesting human approval before an irreversible action.

As models become more capable, the balance shifts between prescriptive guardrails and model judgment. Overly detailed or redundant guardrails can conflict with the model's own reasoning, causing it to follow explicit instructions that diverge from what the context suggests is correct. The same token-efficiency principle from context engineering applies: start with the minimum constraints necessary and add guardrails only in response to observed failure modes.

Guardrails SHOULD be reviewed when switching model versions, since a guardrail written to correct a failure mode in an older model may become unnecessary or counterproductive in a newer one.

== Guides and sensors

It is useful to distinguish two categories of control over agent behavior, borrowed from harness-engineering practice: _guides_ and _sensors_.

*Guides* are feed-forward controls that steer an agent _before_ it acts — `AGENTS.md`, skills, and other instructions loaded into context, anticipating problems and increasing the odds of a good result on the first attempt.

*Sensors* are feedback controls that check an agent's output _after_ it acts — a linter, a type-checker, a test suite, a code review. Sensors are further divided into two kinds:

* *Deterministic sensors* are scripts and tools that give the same verdict on the same input every time. These provide the strongest signal available, because their result does not depend on judgment. Wherever a rule is mechanically checkable, prefer enforcing it with a deterministic sensor over stating it as guidance and hoping the agent follows it.

* An *inferential sensor* is a second agent tasked with judging the output of the first, such as a "review" or "audit" skill. These add value by bringing a fresh perspective, but MUST NOT be treated as a substitute for deterministic checks, because their judgment is itself probabilistic.

An agent steered only by guides repeats the same undetected mistakes indefinitely. An agent checked only by sensors runs an expensive trial-and-error loop with no steering. Reliable agentic workflows need both.

Where an inferential sensor is used, the agent reviewing the output MUST NOT be the same agent, in the same session, that produced it. Models exhibit sycophancy — an agent asked to critique its own recent work is biased toward judging it favorably, whereas a fresh agent with no visibility into the reasoning that produced the work is far more likely to surface real defects. Invoke inferential sensors as distinct agent sessions, and frame the evaluating agent adversarially — instructed to assume the work is broken and to actively verify that claim, rather than to assume it is correct and check for obvious problems — since the latter framing tends to produce agreement with whatever it reads.

== Composable pipelines

An effective agentic workflow is a pipeline of agentic steps and scripted steps, each narrowly scoped, where the output of one step is the input to the next. Scripted steps are the deterministic sensors described above. They catch failure modes and either feed back to an earlier step or escalate to a human.

For a pipeline like this to be composable — so that the same steps can be sequenced differently across different workflows — each step SHOULD be a small, sharp tool with a well-defined input and output, and SHOULD NOT directly invoke or depend on any other specific step. The order in which steps run, and the approval gates injected between them, is the responsibility of whatever orchestrates the workflow, not of the steps themselves.

A workflow is not necessarily a single linear pipeline with one entry point. Work can enter at different points depending on what triggered it:

* *Proactive* paths, triggered by new product requirements — for example, a "specify" step that turns a request into acceptance criteria.

* *Reactive* paths, triggered by bugs or incidents — for example, a "triage" step that classifies an incoming issue.

* *Scheduled* paths, triggered on a recurring interval — for example, an "audit" step that periodically checks the codebase for structural drift.

== Persistence

For one step in a pipeline to hand off to the next — whether that is a different agent, a different session, or a deterministic script — the step's output MUST be persisted to a durable store, not merely held in the conversation. An agent that finishes a planning step and writes its decisions to a plan document has produced something the next agent, in a fresh session with an empty context window, can read and act on. An agent that only states its decisions in the chat has produced nothing the next step can reliably use.

Persisting output to disk also keeps the context window clean. Agentic workflows accumulate noise — exploratory dead ends, intermediate reasoning, tool output that mattered briefly and then stopped mattering. Write only the _distilled_ output of a step — a decision, a plan, a set of findings — rather than carrying the full working history of how that output was produced forward into the next step's context.

Version control — not just any durable store, but one with commits, branches, and history — is the preferred substrate for this persistence. Treat the requirements, decisions, designs, and plans an agentic workflow produces the same way as the code itself. As files committed to version control, not as paragraphs left behind in a chat transcript. This gives every such artifact durability, diff-ability, an audit trail, and a stable path other steps can address it by — the same benefits that version control already provides for code, extended to the rest of what the workflow produces.

== Isolated environments

Persisting state to a shared repository solves handoff between steps that run one after another. But it creates a new problem the moment more than one agent or script operates on that repository at the same time — parallel sub-agents working on independent increments, or a human still working in a checkout while an agent runs against it. Two processes writing to the same working tree concurrently will corrupt each other's work. One process's uncommitted edits become visible, half-finished, to the other. Checked-out branches conflict. And build artifacts and lockfiles collide.

Wherever a workflow runs multiple agents or scripts against a single repository at once, each MUST be given its own isolated working copy rather than sharing one. For most local and agentic workflows, a Git worktree — a second working directory checked out from the same repository, on its own branch, without the overhead of a full clone — is the appropriate mechanism. This lets an orchestrator give each parallel agent its own isolated copy of the codebase, reconciling the resulting branches only at integration time.

This is not always necessary. CI systems typically provide isolation already, by cloning the repository fresh into an ephemeral environment for every job, so there is no shared working tree to corrupt. Whether isolation is needed at all, and which mechanism provides it, is a decision for whoever is orchestrating the workflow, not for the individual steps.

== Prompts

The most important information to include in prompts for agentic workflows is:

* *Role*: Define the specific persona and expertise the agent should adopt.

* *Objective*: State the clear, desired outcome of the task.

* *Constraints*: List the boundaries, standards, or limitations the agent must adhere to.

* *Context*: Provide the necessary background information or existing codebase details.

* *Output Format*: Specify exactly how the result should be delivered (eg. a specific file format or a summary).
