= Reusable context

Most AI coding tools provide mechanisms to reuse context across sessions. The exact naming varies between tools: *instructions*, *rules*, *skills*, *commands* (aka. *custom prompts*). But these all share the same underlying purpose, which is to load prefabricated, reusable bundles of context, either at the start of a session (statically), or on-demand under predefined conditions (dynamically).

Examples include `CLAUDE.md` files and skills in Claude Code, rules in Cursor, and instructions in GitHub Copilot.

All these mechanisms enable *reusable prompt engineering*. They reduce repetition and improve consistency across sessions, by allowing the encoding of programming conventions, architectural decisions, and domain knowledge into artifacts that can be automatically reloaded in fresh AI sessions. This information would otherwise need to be re-communicated manually in every session.

But these tools have a cost. Every token loaded depletes the model's attention budget for the task at hand. Context loaded persistently is context that competes with the user's actual prompt for the model's attention. For this reason, the same core principles of context engineering apply:

* Skills and rules MUST be token-efficient. Start with the minimum content needed to elicit the desired behavior, and grow it only in response to observed failure modes.

* Skills and rules SHOULD be scoped appropriately. Where the tool supports it, use scoping mechanisms (such as directory-specific or pattern-matching rules) to load content only when it is relevant to the task at hand.

* Prefer just-in-time retrieval (see below) over always-on loading. For example, rather than embedding a full coding standard in a rules file, instead provide a pointer to the standard and let the agent load it on-demand.

* Reusable units of context SHOULD be reviewed and pruned regularly. Instructions that were once useful can become stale, redundant, or contradictory as projects evolve. Stale context is worse than no context, because it actively misleads the model.

A practical challenge is that there is no consensus among makers of AI tools on where persistent, reusable context should live, what it should be called, or how it should be structured. If you or your team use multiple AI UIs – or expect to switch between them over time – maintaining the same content in `CLAUDE.md`, `.cursorrules`, `.github/copilot-instructions.md`, and so on, quickly becomes unsustainable. Duplication leads to drift, and drift leads to subtle inconsistencies in behavior between tools.

Nevertheless, some community standards are emerging, and those are the basis for this technical standard's recommendations for designing and managing reusable context.

== The AGENTS.md standard

`AGENTS.md` is an open convention designed to give coding agents a predictable way to understand and operate on software projects. It was jointly launched by Google, OpenAI, Factory, Sourcegraph, and Cursor to replace the fragmentation of tool-specific instructions.

The canonical specification lives at https://agents.md.

`AGENTS.md` is a loose convention rather than a strict standard. Any arbitrary Markdown is supported. While the specification suggests common sections – project overview, dev environment, build/test commands, code style, security, etc. – there is no required structure. Agents are simply required to parse `AGENTS.md` if its exists in the current working directory, else the nearest parent directory.

`AGENTS.md` is widely supported, including by tools such as Cursor, Aider, Gemini CLI, Google Jules, OpenAI Codex, Zed, Factory's Droids, Kilo Code, and Windsurf. (Some of these tools require opt-in via a configuration option or command-line flag). Claude Code also supports it alongside `CLAUDE.md`.

For teams still relying on tool-specific files, a useful transition strategy is to designate `AGENTS.md` as the single source-of-truth and use filesystem symlinks to expose it under each tool's expected filename. This ensures all tools read the same content while moving the project toward the open standard.

The following Markdown template illustrates a minimal `AGENTS.md` file.

[source,markdown]
----
# <Project Name>

## Project overview

A short paragraph describing what this project does, who it is for, and any constraints that materially affect how AI agents should approach changes to it.

## Tech stack

- Language and runtime versions.
- Major frameworks and libraries.

## Repository structure

- `src/`: Application source.
- `tests/`: Automated tests (unit, integration, system).
- `run/`: Dev tools (Bash scripts).
- `docs/`: Developer/maintainer docs, including architectural decision records.
- `skills/`: On-demand context for agents.

## Tools

- `command` to build production-grade artifacts.
- `command` for linting.
- `command` for testing.

## Rules

The capitalized words REQUIRED, MUST, MUST NOT, RECOMMENDED, SHOULD, SHOULD NOT, OPTIONAL, and MAY, in the context of this document and agent skills/instructions/rules, are to be interpreted as described in [IETF RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

- MUST NOT do this.
- SHOULD do this.
- MAY do this.
----

This is a good starter template, which SHOULD be customized as appropriate for the requirements of each project. However, the "repository structure" section is RECOMMENDED in almost all cases. This is one of the highest-leverage things you can give an agent. Without this context, agents will waste valuable tokens grepping around the project's directory tree.

For the rules section, as long as you're using capable models, there is no need to specify universal best practices like "never commit secrets" or "match the prevailing code style". Such knowledge is already embedded in models that are optimized for coding tasks. Instead, list quality requirements that are specific to your project, such as "minimum 75% unit test coverage" and "conforms to neostandard linter defaults".

Other sections you might consider including in `AGENTS.md` include "code formatting conventions", "design patterns", "testing instructions", "pr creation", and "security standards". Start with a minimum baseline then extend your agent instructions incrementally to improve output.

== Agent skills

*Agent Skills* is a complementary open convention for packaging reusable, task-scoped bundles of context that agents can load on demand. Whereas `AGENTS.md` provides a static, always-loaded orientation to the project as a whole, skills encapsulate specific procedures, standards, runbooks, or playbooks that are only relevant to certain tasks.

The canonical specification for Agent Skills lives at https://agentskills.io/specification.

=== Loading skills

By combining `AGENTS.md` with agent skills, you can manage persistent context in a token-efficient way. You do this by instructing agents (via `AGENTS.md`) to load task-specific guidance through just-in-time retrieval (via skills).

Here's an extended `AGENTS.md` template, now with a "skills" section. It demonstrates how both local skills (which live inside or near the current repository, referenced via relative file paths) and global skills (which are fetched from calls to absolute URLs) can be used together. Local skills are unique to the project, while global skills are reused across projects.

[source,markdown]
----
# <Project Name>

## Project overview

A short paragraph describing what this project does, who it is for, and any constraints that materially affect how AI agents should approach changes to it.

## Tech stack

- Language and runtime versions.
- Major frameworks and libraries.

## Repository structure

- `src/`: Application source.
- `tests/`: Automated tests (unit, integration, system).
- `run/`: Dev tools (Bash scripts).
- `docs/`: Developer/maintainer docs, including architectural decision records.
- `skills/`: On-demand context for agents.

## Tools

- `command` to build production-grade artifacts.
- `command` for linting.
- `command` for testing.

## Rules

The capitalized words REQUIRED, MUST, MUST NOT, RECOMMENDED, SHOULD, SHOULD NOT, OPTIONAL, and MAY, in the context of this document and agent skills/instructions/rules, are to be interpreted as described in [IETF RFC 2119](https://www.ietf.org/rfc/rfc2119.txt).

- MUST NOT do this.
- SHOULD do this.
- MAY do this.

## Skills

- `./skills/release/SKILL.md`: Checklist for cutting a release.
- `./skills/migration/SKILL.md`: Guidance for writing database migrations.
- `../skills/code-review/SKILL.md`: Generic code review checklist.
- `https://example.com/standards/api-design/tree/main/SKILL.md`: API design conventions.
----

You may need to adjust your skill-loading mechanism, depending on the structure of your projects and the agents you're using. The industry has not yet settled on standard conventions here.

Some agents will automatically load user-level skills stored in various locations in your home directory, which can be a useful way of sharing skills across multiple projects.

[TIP]
======
See the excellent https://github.com/JuliusBrussee/caveman/[Caveman] project, which demonstrates how to install the same skill across multiple agents. It also demonstrates how to evaluate the effectiveness of skills.
======

An emerging best practice is to define a small set of common _workflows_ as user-level and project-level skills, while keeping _knowledge_ (standards, policies, constraints, domain models, etc.) as separate reference documents that are loaded on-demand from user-level and project-level skills. Workflow skills should be for things like "planning", "coding", "testing", "deploying", and "releasing". They should be step-by-step, deterministic instructions, free of domain-specific facts.

Your workflow skills should rarely change, even between domains. By comparison, reference materials that encapsulate standards, policies, constraints, and domain models are dynamic and volatile – changing constantly.

This separation is also what makes a workflow skill reusable across projects. A skill that only says _how_ to look something up, and what to do with it once found, stays technology-agnostic and domain-agnostic, and can run unmodified against any project that supplies its own reference material on demand. A skill that hard-codes project-specific knowledge stops being portable the moment it leaves the project it was written for. If a piece of knowledge genuinely belongs nowhere but one project, keep it local to that project rather than baking it into a shared skill.

Pulling this knowledge dynamically helps to keep your agentic workflows evergreen. This separation of concerns will also help you to debug issues with your agents:

When something goes wrong, you can ask:

* “Did the workflow break?” → skill issue.
* “Did the knowledge change?” → retrieval issue.

=== Skill structure

A skill is a directory containing, at a minimum, a `SKILL.md` file. The directory MAY also contain `scripts/`, `references/`, and `assets/` subdirectories – for executable code, supplementary documentation, and static resources, respectively.

----
skill-name/
├── SKILL.md          # Required: metadata + instructions.
├── scripts/          # Optional: executable code.
├── references/       # Optional: extended documentation.
├── assets/           # Optional: templates, schemas, other resources.
└── ...
----

A skill directory MAY contain other artifacts that are not defined by the Agent Skills specification. This technical standard RECOMMENDS including a `README.md` file for documenting the use of the skill for the benefit of its human users.

The `SKILL.md` file MUST contain YAML front-matter followed by a Markdown body. Two front-matter fields are required:

* `name`: 1-64 characters of lowercase alphanumerics and hyphens (no spaces or punctuation). SHOULD match the parent directory name, though this is not a requirement of the standard.

* `description`: 1-1024 characters describing both _what_ the skill does and _when_ to use it. The description carries the entire burden of triggering the skill: at startup, agents load only the `name` and `description` fields; the full `SKILL.md` body is read only if the description matches the current task. If the description fails to match, the skill never activates — regardless of the quality of its instructions.
+
Four principles produce effective descriptions: use imperative phrasing ("Use this skill when…" rather than "This skill does…"); focus on user intent, not implementation detail; err on the side of explicitness — list every context where the skill applies, including cases where the user may not name the domain directly; and stay under the 1024-character hard limit (content beyond it is silently truncated). Note also that skills activate only for tasks requiring specialized knowledge, unfamiliar APIs, or domain-specific workflows — not for simple requests the agent can handle unaided, even when the description semantically matches.

Different tools handle skill loading differently. The Agent Skills specification targets _on-demand_ activation. The agent reads each skill's `description` field and decides whether to load it based on the current task. Some tools also support _always-on_ loading, where the skill is injected at the start of every session, or _manual_ loading, where the user triggers the skill via a slash command. UIs such as Cursor, Windsurf, and Cline load their native rule files persistently – so the token-efficiency principle becomes even more critical.

When writing a skill intended for broad deployment across multiple tools, check how each target tool resolves and activates skills, as the loading mechanism affects both `description` field strategy and the overall context budget.

Optional fields include `license`, `compatibility` (environment requirements), `metadata` (arbitrary key-value pairs), and `allowed-tools` (a space-separated list of tools that are pre-approved to be run by the agent – currently experimental). Individual tools support additional proprietary fields, too. So you may wish to optimize your skills definitions based on the capabilities of your chosen harness – see, for example, https://github.com/anthropics/skills/[Anthropic's] and https://code.visualstudio.com/docs/copilot/customization/agent-skills[VS Code's] documentation for agent skills.

The Markdown body after the front-matter contains the agent's instructions – context that will be passed to the LLM. As with `AGENTS.md`, there is no specific required structure for this section. You are free to design the information architecture on a case-by-case basis, as required to optimize knowledge transfer to the AI. Guidelines for producing effective information architectures are described later in this section.

Once an agent has decided to use a skill, it will load the full body content of the `SKILL.md` file into the context window. However, further *progressive disclosure* is supported through the use of the OPTIONAL `scripts/`, `references/`, and `assets/` directories, which MUST be siblings of the `SKILL.md` file.

The `scripts/` directory contains executable code that agents are allowed to run. The following principles apply to scripts intended for agentic use:

*No interactive prompts.* Agents operate in non-interactive shells and cannot respond to TTY prompts, password dialogs, or confirmation menus. A script that blocks on input will hang indefinitely. All input MUST be supplied via CLI flags, environment variables, or stdin — never via interactive prompts.

*`--help` as the agent's primary interface.* `--help` output is how the agent learns a script's interface before running it. It SHOULD be concise (it enters the context window) and SHOULD include a description, all supported flags, and a usage example.

*Self-contained dependencies.* Scripts SHOULD be self-contained. For Python scripts, PEP 723 inline metadata (used with `uv run`) lets a script declare its own dependencies without a separate manifest or install step. Deno and Bun support similar inline package specifiers. When a script cannot be fully self-contained, its dependencies MUST be clearly documented at the top of the file.

*One-off commands.* For simple tasks, tools such as `uvx`, `npx`, and `bunx` can invoke packages directly from `SKILL.md` instructions without a `scripts/` directory at all. Pin versions for reproducibility — for example, `npx eslint@9.0.0`.

*Stdout/stderr separation.* Structured output data goes to stdout. Progress messages, diagnostics, and warnings go to stderr. This lets the agent capture clean, parseable output while still seeing diagnostic information.

*Idempotency.* Agents may retry commands on failure. Where possible, scripts SHOULD be idempotent: a "create if not exists" pattern is safer than "create and fail on duplicate."

*Output size management.* Many agent harnesses truncate tool output beyond a threshold (typically 10–30K characters). Scripts that may produce large output SHOULD default to a summary view and SHOULD support a `--limit`/`--offset` flag for pagination, or an `--output FILE` flag to write to a file rather than stdout.

Scripts SHOULD include helpful error and success outputs to give agents usable feedback, and MUST handle edge cases gracefully to prevent agent failure. Different agents support different languages, but it is RECOMMENDED to use a widely-supported subset – Bash, Python, and JavaScript, for example.

The `references/` directory captures additional documentation that agents can read when needed. Each file SHOULD be focused on a specific topic. When referencing these files from `SKILL.md`, include an explicit trigger condition rather than a generic pointer. _"Read `references/api-errors.md` if the API returns a non-200 status code"_ is more useful than _"see `references/` for details"_. If you do this, agents load context on demand, not speculatively – conserving valuable context space.

Finally, the `assets/` directory contains static resources such as templates, images, and data files.

[TIP]
======
It is RECOMMENDED to keep `SKILL.md` files under 500 lines. Extract extended materials to scripts, references, and assets.

=== Authoring skill content

The challenge of writing agent skills is producing effective content. A common pitfall is asking an LLM to auto-generate a skill without providing it with domain-specific context, so relying on the model's general training knowledge. The result is vague, generic advice ("handle errors appropriately", "follow best practices for authentication") rather than the specific patterns, edge cases, and conventions.

Skills will be genuinely useful to agents, improving their performance, if they supply knowledge that is not already known to the models you use.

A useful concrete test for every instruction in a skill: _"Would the agent get this wrong without this instruction?"_ If not, cut it. Think of a well-crafted skill as the onboarding document you would write for a qualified new employee. Include only what they cannot independently discover: domain knowledge, edge cases, internal conventions, and product philosophy. Universal best practices that a capable agent already knows add token cost without adding value.

When scoping a skill, aim for a coherent unit of work — analogous to how you would scope a well-designed function. Too narrow a scope forces the agent to load multiple skills for a single task, increasing overhead and the risk of conflicting instructions. Too broad a scope makes precise activation harder and dilutes the signal-to-noise ratio of the content. A skill that queries a database and formats results is likely a coherent unit; one that also covers database administration is probably too broad.

Aim for moderate detail rather than exhaustive coverage. Overly comprehensive skills can hurt more than they help — the agent struggles to extract what is relevant and may pursue unproductive paths. Concise stepwise guidance with a working example tends to outperform exhaustive documentation. When you find yourself wanting to cover every edge case, consider whether most are better left to model judgment.

Effective skills are grounded in real expertise. Two approaches are recommended:

*Extract from a hands-on task.* Complete a real task in conversation with an agent, providing context, corrections, and preferences along the way. Pay attention to the sequence of actions that led to success, corrections you made, input and output formats, and project-specific context you had to supply that the agent didn't already know. Then crystallize that experience into a new skill for reuse next time you tackle the same problem.

*Synthesize from project artifacts.* When you have a body of existing knowledge, feed it into an LLM and ask it to synthesize a skill. Effective source material includes internal documentation, runbooks, and style guides; API specifications and configuration files; code review comments and issue trackers; version control history (especially patches and fixes); and real-world failure cases and their resolutions. A skill synthesized from your team's actual incident reports will outperform one generated from a generic "best practices" article, because it captures your specific failure modes and recovery procedures.

=== Evaluating and refining skills

After authoring a first draft, refine it by running the skill against real tasks and reading full execution traces — not just the final outputs. A useful practice: use the same CLI or headless interface the agent uses, so you experience what it experiences. Review actual execution traces directly rather than inferring from end results, and convert any friction you discover into test cases.

Common failure signals to look for in traces are:

* instructions that are too vague (the agent tries multiple approaches before finding one that works);
* instructions that don't apply to the current task (the agent follows them anyway);
* too many options presented without a clear default (the agent picks arbitrarily).

Even a single pass of execute-then-revise noticeably improves quality.

*Structured evaluation.* For more rigorous testing, build a test suite. A standard convention is to store test cases in `evals/evals.json` inside the skill directory. Each test case has three components: a realistic user prompt, a human-readable description of what success looks like, and optional input files.

The central mechanism of skill evaluation is running every test case in two configurations: with the skill, and without it (or against the previous version). The *delta* — the difference in pass rate, latency, and token consumption between configurations — tells you what the skill costs versus what it buys. A skill that does not improve the pass rate is not earning its context cost.

A useful three-condition comparison:

1. the agent without the skill;
2. the agent with a minimal equivalent instruction (a single sentence);
3. the agent with the full skill loaded.

If the skill does not clearly outperform the single-sentence instruction, it should be condensed or reconsidered.

*Assertions.* Do not over-specify assertions upfront. After the first run, observe what the skill actually produces and then write verifiable checks based on those outputs. Strong assertions are objective and evidence-backed — for example, "the output contains a labeled bar chart"; weak ones are vague ("output is good") or brittle (exact phrase matching). Reserve assertions for objective checks; subjective quality belongs in human review. For a complementary holistic assessment, present outputs from two skill versions to an LLM judge without indicating which is which. This blind comparison grades qualitative properties — organisation, formatting, usability — that are hard to express as assertions.

*Pattern analysis.* After grading, analyze patterns across the test suite:

* Remove assertions that always pass in both configurations — they test nothing.
* Investigate assertions that always fail — the assertion itself may be incorrect.
* Study assertions that pass only with the skill — this is where the skill adds value.
* Tighten instructions wherever results are inconsistent across runs — high variance signals ambiguous instructions.

*Activation quality.* Check whether the skill loads on the right prompts and stays dormant on irrelevant ones. The `description` field is the primary lever for controlling this. When building negative test cases for activation quality, prioritize near-miss cases: prompts that share keywords or concepts with the skill but require something different. Obvious negatives ("write a fibonacci function") test nothing about a deployment skill. Near-miss negatives — prompts that mention your skill's domain but need a different approach — are far more informative.

*Iterating.* When iterating on a skill based on test results, generalize from failures rather than patching specific test cases. Over-constraining instructions causes skills to plateau or regress. Reasoning-based instructions — those that explain _why_, not just _what_ — tend to outperform rigid directives; an agent that understands the purpose behind an instruction makes better context-dependent decisions. If you find the agent reinventing the same logic across runs, bundle that logic into `scripts/` rather than repeating it in prose instructions.

The https://github.com/anthropics/skills/tree/main/skills/skill-creator[`skill-creator`] skill, provided by Anthropic, automates much of this evaluation and iteration loop end-to-end.

=== Single responsibility

A skill SHOULD have exactly one responsibility, corresponding to a single step in a workflow. It SHOULD define one job and stop at a well-defined boundary, rather than reaching into adjacent work even where doing so would be convenient.

In particular, a skill SHOULD NOT combine _evaluation_ and _implementation_ in one responsibility. A skill that analyzes and reports findings (a review, an audit, a proofread) is a different kind of thing from a skill that enacts a change (a fix, a migration, a refactor), and the two SHOULD NOT be bundled into one skill. For example, a skill that reviews a pull request should not also be the skill that applies the fixes it recommends — the decision of whether, when, and how to act on findings belongs to whoever is orchestrating the workflow, not to the skill that produced them.

Keeping evaluation and implementation apart has practical benefits: an orchestrator can review findings before any change is applied; each skill gets a single, unambiguous trigger condition; and an evaluation skill becomes reusable in contexts its author did not anticipate — for example, the same review skill that supports a human pull request can be wired into a CI gate.

=== Loose coupling

Where multiple skills are composed into a workflow, they SHOULD be loosely coupled to one another. A skill SHOULD NOT directly invoke, refer to, or hand off to another skill by name. Each skill does its one job, reports its result, and stops. The composition of skills into a sequence is the responsibility of whatever is orchestrating the workflow — a human, a script, or another agent — not of the skills themselves.

This means a skill's output should be usable as the input to whichever skill runs next, without either skill being aware of the other's existence. Coupling skills through their inputs and outputs rather than through direct references keeps each skill independently maintainable, and lets the same skill be reused in workflows its author never anticipated.

=== Interface definitions

A skill SHOULD be explicit about its inputs and outputs, in the same way a well-designed function is explicit about its parameters and return value. This RECOMMENDS documenting, for each skill:

* What input it consumes, and whether that input is OPTIONAL or REQUIRED.

* Whether the skill requires an interactive session — one in which the agent is free to prompt the user for further input — or can run non-interactively to completion.

* What output it produces, in what format, and where that output is written (a file, a comment, a commit, the conversation itself).

* What success criteria the output should be checked against.

This input/output contract is what lets a human or an orchestrating script decide where a skill fits in a larger workflow, how to wire its output into the next step, and how to validate what it produced.

=== Interactive versus non-interactive

A skill SHOULD state whether it can run non-interactively – taking only its initial input and proceeding to completion without stopping to ask the user – or whether it is necessarily interactive, blocking to ask questions, present options, and wait for answers.

Non-interactive skills can be run unattended, including by parallel sub-agents. Interactive skills SHOULD be used sparingly, reserved for cases where human interaction _is_ the value the skill provides — a structured discovery interview, for example, where the dialogue itself is the point, rather than an obstacle to be designed around.

=== Calibrating control

Not every part of a skill needs the same level of prescriptiveness. Match the specificity of instructions to the fragility of the task. Here are some guidelines:

*Give the agent freedom* when multiple approaches are valid and the task tolerates variation. In these cases, explaining _why_ is often more effective than specifying exact steps. An agent that understands the purpose behind an instruction makes better context-dependent decisions.

*Be prescriptive* when operations are fragile, consistency is critical, or a specific sequence must be followed. If a script must be run with exact flags, say so explicitly.

*Provide defaults, not menus.* When multiple tools or approaches could work, pick one as the default and mention alternatives as escape hatches, rather than presenting them as equal options. The agent should follow the default unless there is a specific reason not to.

*Favor procedures over declarations.* A skill should teach the agent _how to approach_ a class of problems, not what to produce for a specific instance. A reusable method that generalizes across tasks is more valuable than a hardcoded answer to a single question. Specific details – output templates, tool flags, constraints – can still be included where they are stable.

=== Effective instruction patterns

As with `AGENTS.md`, the body content of a `SKILL.md` file can be any freeform text. You are encouraged to experiment and to design an information architecture on a skill-by-skill basis to optimize outcomes. Nevertheless, some best practices have emerged from information architectures that have proven to be consistently effective across multiple agents and models.

*Step-by-step instructions.* For multi-step workflows, an explicit `- [ ] Step N` checklist helps the agent track progress and avoid skipping steps that have dependencies or validation gates.

*Output format templates.* When you need the agent to produce output in a specific format, provide a concrete template rather than a prose description. Agents pattern-match against structure more reliably than they interpret descriptions. Short templates can live inline in `SKILL.md`. Longer or conditionally-needed templates belong in `assets/`.

*Validation loops.* Instruct the agent to run a validator after completing work, fix any failures, and repeat until validation passes before moving on. The validator may be a script, a reference checklist, or a self-check against stated criteria.

*Plan-validate-execute.* For batch or destructive operations, have the agent produce an intermediate plan in a structured format, validate it against a source of truth, and only then execute. The key ingredient is a validation step that produces error messages specific enough for the agent to self-correct without human intervention.

*Bundle reusable scripts.* If you notice the agent reinventing the same logic across runs – building a chart, parsing a format, validating output – write it once as a tested script in `scripts/` and reference it from the skill.

*Gotchas* A dedicated section – named "edge cases", for example – that lists environment-specific facts that defy reasonable assumptions is often the highest-value content in a skill. These are not general advice but concrete corrections to mistakes the agent will make without being told otherwise: wrong field names, soft-delete filters, misleading health-check endpoints, non-obvious API constraints. Keep gotchas in `SKILL.md` itself – not a reference file – because the agent needs them before it encounters the situation. When an agent makes a mistake you have to correct, add the correction to the edge cases section.

=== Sharing skills

Skills can be shared and reused across projects by hosting them at a publicly accessible URL and referencing them as global skills in `AGENTS.md`.

The https://www.skills.sh/[Agent Skills Directory] (skills.sh) is the primary public registry for discoverable, installable skills. Skills listed there can be installed into any project via `npx skillsadd <owner/repo>` and referenced via their raw URLs.

When designing a skill for public sharing rather than internal project use, additional considerations apply:

* *Avoid project-specific assumptions.* Internal skills can reference your schemas, tools, and conventions directly. Shared skills must instead teach a pattern that transfers across different projects and environments.

* *Document prerequisites clearly.* Use the `compatibility` field to specify runtime requirements, and describe any dependencies – tools, language versions, environment variables – at the top of `SKILL.md`.

* *Provide working examples.* Public audiences have less context than your internal team. A small set of concrete input/output examples significantly reduces the friction of adoption.

* *Keep skills current.* Use the `metadata` field to record a `last_updated` date, and review shared skills whenever the underlying tools or APIs change. A widely-referenced skill that becomes stale can cause failures across many projects.

Before publishing, validate a skill's skill configuration with the `skills-ref` package:
https://github.com/agentskills/agentskills/tree/main/skills-ref
