# TS-8: Issue Tracking

This is a compact version of technical standard TS-8 for AI agents.

Use this when creating, triaging, or reviewing issues (tasks, tickets, work
items) in an issue tracker, or when designing issue-tracking workflows and
boards. Covers issue types, the issue lifecycle, ownership of trackers, and
the relationship between issues and version control.

Do NOT use this for higher-level project/roadmap planning — that belongs in
separate project-management tools (see "Keep the tracker focused" below).
[TS-9: Version Control](../009/AGENTS.md) covers how issues map to branches and
commits.

## Rules

- **Every project MUST have an issue tracker, and it is the authoritative source
  for all work.**

  Every significant change to the source code or configuration of a software
  component MUST be initiated by opening a new issue in that component's tracker.
  Exceptions MAY be made for small "chores" (see
  [TS-9: Version Control](../009/AGENTS.md)) that do not alter configuration or
  behavior.

- **Each issue MUST have a unique identifier.**

  Auto-generated by most trackers. Used to cross-reference issues and to create
  references from commits, branches, and pull requests.

- **Each issue MUST be scoped to exactly one small, discrete change.**

  An incremental update to behavior or configuration, or a small iteration in
  internal design. An issue MAY be small enough for a single atomic commit, or
  MAY use a temporary branch over multiple commits (see
  [TS-9: Version Control](../009/AGENTS.md)). Each issue MUST clearly define the
  goal for implementing the change — having a reason for every change keeps
  scope small and focused.

- **Each issue SHOULD be assigned a primary type.**

  One of: Bug, Dev, Epic, Errata, Feature, Incident, Maintenance, Refactoring,
  Runtime, Spike, Support, Task, Vulnerability (see Issue Types below). Rarely,
  secondary types MAY be assigned when an issue legitimately spans multiple
  types; the primary type MUST clearly communicate the principal intent. Where
  the tracker supports custom issue types with unique fields/templates, using
  them is RECOMMENDED.

- **Trackers SHOULD be directly attached to source code repositories.**

  Integration benefits: unified workflow (issues initiate all work), automated
  state transitions on version-control events, automatic closure on merge,
  bidirectional cross-referencing between commits/branches/PRs and issues,
  branch lifecycle management, and complete lifecycle tracking. One tracker
  per repository is best practice, but a single tracker across multiple
  repositories is also common. See [TS-9: Version Control](../009/AGENTS.md).

- **Issue trackers MUST be owned by development and operations teams.**

  They MUST NOT be controlled by product managers, delivery managers, or other
  business-oriented roles. Product managers (or other customer/business
  representatives) SHOULD NOT have write access except to log bugs and incidents
  as any other user would. Tasks to implement business requirements MUST be
  added by the development teams, in collaboration with product managers.

- **Keep the issue tracker focused on ephemeral work.**

  Issues are short-lived by design — they open, get worked, and close; the
  lifespan of an issue SHOULD be short. Issue trackers SHOULD NOT be used to
  manage feature requests, requirements specifications, product roadmaps, or
  long-term backlogs. Requirements specifications and architectural decisions
  SHOULD be maintained as documents under version control, co-located with the
  source code they describe (portable across trackers, durable across tool
  migrations, reviewable via pull requests). For open source projects, feature
  requests SHOULD go to a discussion forum (eg. GitHub Discussions), not the
  tracker. Higher-level cross-repository/cross-team coordination MAY use
  additional project-management tools, but those tools SHOULD NOT be the primary
  mechanism for managing technical work.

- **Issues MUST change state as work progresses.**

  Lifecycle states MUST accurately model the real-world development process,
  which varies by project and team. Common starting-point states: **Open**
  (created, no work yet — the "backlog"), **Development** (actively worked),
  **Review** (complete, awaiting peer/lead review), **Testing** (reviewed,
  passing QA gates), **Closed** (complete). The tracker is the single source of
  truth for work state regardless of how it is represented in version control.

- **Issues SHOULD be represented on boards, organized at the team level.**

  Boards provide a visual indication of progress for the whole team — they MUST
  be organized at the team level, not the individual level. Keep boards simple
  and lightweight: avoid overloading with target release dates, estimations,
  and time tracking. They are a development tool, not a project-management tool.

- **Interim-state issues SHOULD be assigned to at least one team member.**

  Assignees are responsible for progressing the ticket and are the point of
  contact for enquiries. Assignment MAY change over time. Multiple people MAY
  work on a ticket simultaneously (eg. pair programming). As a general rule,
  individual contributors SHOULD be assigned to just one ticket at a time;
  exceptions MAY be made when a ticket is repeatedly blocked. Issues and their
  associated branches SHOULD have clear ownership and be kept in sync (see
  [TS-9: Version Control](../009/AGENTS.md)).

## Issue types

The 13 primary issue types. Use the decision tree at the end of this section to
pick the right type.

- **Bug** — Defects, errors, or regressions in expected behavior (functional
  or non-functional, eg. latency/availability), discovered in production or a
  production-like environment. Every identified bug MUST be logged; one issue
  per bug unless multiple bugs share a likely root cause (then MAY be merged).
  Bug issues SHOULD capture step-by-step reproduction instructions, expected vs
  actual outcomes, relevant runtime environments, and other artifacts
  (screenshots, stderr output).

- **Dev** — A small, incremental change to code or configuration that
  contributes toward delivering value (a feature, refactoring, bug fix, etc.).
  By definition always involves code/config changes. Most granular dev work
  does not need formal tracking; record a dev issue when you want a reminder,
  to make a small task visible, or to capture work that fits no other category.
  Dev issues SHOULD be kept small in scope; if complexity grows, consider a
  more specific type.

- **Epic** — A parent container grouping multiple related issues that together
  deliver value. Where multiple issues need completing to deliver value to one
  or more stakeholder groups, they SHOULD be grouped under a single epic.
  Granularity is flexible (multi-month initiatives, feature areas, or small
  features broken into tasks); teams SHOULD choose appropriate granularity.
  Epics MAY span multiple repositories.

- **Errata** — Mistakes, inaccuracies, or omissions in documentation or other
  written content (user-facing docs, API specs, inline code comments, ADRs,
  contribution guidelines, READMEs). Errata are distinct from bugs: bugs
  describe incorrect software behavior; errata describe incorrect
  documentation. If documentation accurately describes current behavior that is
  itself wrong, the issue is a bug. Errata SHOULD identify the location of the
  mistake and propose a correction where possible.

- **Feature** — MUST be used to specify new or modified functionality, or to
  propose that existing operations/behaviors be deprecated, removed, or
  superseded, before implementation. Features originate from functional
  requirements (FRs) in the SRS. Features SHOULD be specified using a consistent
  convention for acceptance criteria (eg. user stories, use cases) describing
  the feature from the perspective of the users who benefit (see
  [TS-1: Software Requirements Specification](../001/AGENTS.md)). If changes
  have no implications for system operations or behaviors, it is not a feature
  (likely a bug or improvement work).

- **Incident** — An unplanned event that disrupts normal operations of a
  production system or degrades its performance: outages, security breaches,
  data loss, etc. Special issue types MUST be used to track analysis and
  resolution; ideally added automatically. Relevant only to software services,
  not to shrinkwrap software, libraries, or other non-service components.

- **Maintenance** — General housekeeping and ad hoc chores necessary in the
  upkeep of a system: routine dependency upgrades, configuration of tools and
  infrastructure, improvements to artifacts like documentation, test scripts,
  and requirements specs (anything except source code and config from which
  executables are compiled). May involve refactoring for compatibility with
  breaking API changes in updated dependencies — in which case a refactoring
  issue may be more appropriate.

- **Runtime** — Tracks implementation of non-functional requirements (NFRs /
  quality requirements / QRs), also known as dynamic quality attributes
  (availability, consistency, latency, security, compliance). NFRs are
  cross-cutting concerns that tend to impact fundamentals (internal code
  structure, data structures, database/infrastructure choices) and are
  relatively expensive to retrofit — quality constraints SHOULD be specified
  early. NFRs MAY emerge over time (eg. growing from 10 to 1,000 concurrent
  searches); dedicated issues SHOULD be raised to track the necessary changes.
  Where possible, specify metrics to benchmark against (MTBF, MTTR, crash rate,
  open/close rates of incidents, user analytics) or acceptance criteria in
  terms of conformance to published standards (AES-256, TLS, WCAG, GDPR).

- **Refactoring** — Work to refactor code or configuration to make the system
  easier to develop and maintain, without changing existing features or
  performance. Focus is on developer/maintainer needs, not users. Refactoring
  SHOULD be undertaken as a normal part of feature, performance, and bug-fix
  work — in-flight refactoring SHOULD be scoped only to what is necessary to
  support the change. When up-front or after-the-fact design changes are
  required before/after new features, refactoring SHOULD be undertaken as
  separate work items and tracked with refactoring issues, which SHOULD be
  linked to dependent feature issues. Consider "technical debt" framing;
  capture short-term costs/risks vs long-term benefits, and any measurable
  impact (test coverage, LOC reduction, Cyclomatic Complexity/NPath).

- **Spike** — A short, focused, time-boxed period (typically 1–2 days to a
  week) of work to explore or investigate a technical challenge, uncertainty,
  or decision point: rapid prototyping, researching tools/libraries/approaches,
  testing feasibility, clarifying unknowns. Spikes do not aim to produce
  production-ready code — just insight (findings, recommendations, proof of
  concept).

- **Support** — Requests for technical help (troubleshooting, configuration
  assistance, advice on how to use the software). In open source projects these
  may be raised by end users; in proprietary SaaS, by downstream users in the
  same organization. May be generated automatically from helpdesk systems or
  raised manually by users or support staff.

- **Task** — Work that does not involve changes to code or configuration:
  operational work, personnel management, permission/role adjustments,
  organizational activities, or other work outside the codebase. Unlike dev
  issues, tasks never modify code, config, or other repository artifacts. If
  work could be more precisely categorized under another type, prefer that type.
  Task issues SHOULD be used only when no other type is a good fit.

- **Vulnerability** — A weakness in the software, its dependencies, or its
  infrastructure that could be exploited to compromise confidentiality,
  integrity, or availability. Distinct from bugs: vulnerabilities are
  weaknesses that create security risk regardless of whether the system
  malfunctions under normal conditions. Examples include command injection,
  broken authentication, IDOR, XSS, insecure deserialization, use of components
  with known CVEs, and infrastructure/access-control misconfigurations.
  Vulnerability issues SHOULD be treated as sensitive: where the tracker
  supports private/confidential issues, file them privately and disclose
  publicly only after a fix is released. Severity SHOULD be assessed using a
  recognised scoring system (eg. CVSS); at minimum classify as critical, high,
  medium, or low. Third-party vulnerabilities SHOULD reference the relevant
  CVE identifier(s); dependency-scanning output SHOULD be attached or
  summarised. Resolution urgency SHOULD be proportional to severity; critical
  and high severity SHOULD be prioritized above other work.

### Decision tree

Use this to determine the appropriate issue type:

```
Does this involve changes to code or configuration?
│
├─ NO ─── TASK
│
└─ YES
   │
   ├─ Is this fixing a problem?
   │  │
   │  ├─ YES
   │  │  │
   │  │  └─ Is it in documentation or other content?
   │  │     │
   │  │     ├─ YES ─── ERRATA
   │  │     │
   │  │     └─ NO
   │  │        │
   │  │        └─ Is it a security issue?
   │  │           │
   │  │           ├─ YES ── VULNERABILITY
   │  │           └─ NO ─── BUG
   │  │
   │  └─ NO ───┐
   │           │
   ├─ Does this change system behavior from the user's perspective?
   │  │
   │  ├─ YES ─── BEHAVIOR
   │  │
   │  └─ NO ────┐
   │            │
   ├─ Is this about a runtime quality attribute (latency, availability, security, etc.)?
   │  │
   │  ├─ YES ─── QUALITY
   │  │
   │  └─ NO ────┐
   │            │
   ├─ Is this about code structure, design patterns, or internal improvements?
   │  │
   │  ├─ YES ─── REFACTORING
   │  │
   │  └─ NO ────┐
   │            │
   ├─ Is this an investigation, prototype, or feasibility study?
   │  │
   │  ├─ YES ─── SPIKE
   │  │
   │  └─ NO ────┐
   │            │
   ├─ Is this routine maintenance or operational work?
   │  │
   │  ├─ YES ─── MAINTENANCE
   │  │
   │  └─ NO ────┐
   │            │
   ├─ Is this a request for technical help from a user?
   │  │
   │  ├─ YES ─── SUPPORT
   │  │
   │  └─ NO ────┐
   │            │
   ├─ Is this an unexpected event that disrupted production?
   │  │
   │  ├─ YES ─── INCIDENT
   │  │
   │  └─ NO ────┐
   │            │
   ├─ Is this a small incremental change that contributes to a larger effort?
   │  │
   │  ├─ YES ─── DEV
   │  │
   │  └─ NO ────┐
   │            │
   └─ Will multiple increments of work be required?
      │
      ├─ YES ─── EPIC
      │
      └─ NO ─── TASK
```
