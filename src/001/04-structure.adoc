= Structure of a specification

A specification SHOULD be organized so that every category of requirement has a
single, unambiguous home. The objective is for no requirements to be left
undocumented.

The taxonomy below is RECOMMENDED by this technical standard.

----
specification/
│
├── context/                  Descriptive — the problem space.
│   ├── overview/               Mission, problem, scope.
│   ├── constraints/            Regulatory/legal/business constraints + assumptions + dependencies.
│   ├── glossary/               Ubiquitous language.
│   ├── model/                  Domain entities, relationships, ERD.
│   └── actors/                 Participants + hierarchy (definitions only — no permissions).
│
└── requirements/             Prescriptive — the contract.
    ├── behaviors/              Functional requirements.
    │   ├── access/               Permission matrix — which actors may exercise which capabilities.
    │   ├── rules/                Invariants, policies, lifecycle transitions.
    │   ├── features/             Gherkin scenarios.
    │   ├── journeys/             Wireframes and/or call-sequences.
    │   └── interfaces/           External contract: operations, resources, events.
    └── qualities/              Non-functional requirements.
----

== Context versus requirements

The top-level split is between context (what _is_) and requirements (what
_must be_).

*Context* is descriptive. This part of the specification covers the domain, its
vocabulary, its participants, and the conditions the system operates within.
None of it is a requirement in its own right. Rather, the context is the shared
frame of reference from which requirements are derived.

*Requirements* are prescriptive. Every statement is an obligation that can, in
principle, be verified against the running system.

Keeping the two apart means a reader always knows whether they are reading
background or a binding commitment. The separation prevents descriptive material
from quietly accreting the force of a requirement.

== Constraints versus requirements

Constraints are context, not requirements. A regulatory or contractual constraint
may read like a requirement, but it is actually a boundary set by the world — a
law, a contract, a dependency, a standing assumption — not a behavior the system
chooses to exhibit.

Where a constraint implies a testable obligation, that obligation is restated as
a rule or a quality, and cross-references back to the constraint. Thus, the
constraint remains purely descriptive.

== Functional versus non-functional requirements

The classic "`functional versus non-functional`" distinction survives one level
down, as _behaviors_ versus _qualities_.

_Qualities_ is a catch-all for dynamic qualities observed externally of the
system at runtime. This covers requirements for performance (throughput and
latency), availability, security, compatibility, portability, and so on.

Internal, static qualities such as maintainability and extensibility are a
design concern, and SHOULD be documented elsewhere — keep them out-of-scope
of the software requirements.

== Actors versus access

Actors define _who_ participates in the software system. _Access_ defines what
each participant is permitted to do.

Splitting these two concerns into separate artifacts allows them to be kept on
different sides of the context/requirements line. Actors are part of the domain
model, which is background context. Access rules are requirements that the system
is expected to enforce.

The permission matrix, which maps actors to capabilities, therefore has a single
authoritative home.

== Rules versus features

A feature is a concrete, scenario-level behavior. Policies (eg. "`a pet can't be
reserved and sold at the same time`") and validation constraints are cross-cutting
concerns that tend to span multiple features. Therefore, if we specified policies
and validation constraints at the level of features, we'd get duplication of
these requirements, leading inevitably to drift.

The solution is to state policies and validation constraints as business rules
in one central place. Each rule gets a single authoritative statement with a
stable identifier that scenarios can cross-reference.

Similarly, entity lifecycle rules live under business rules, not in the domain
model. The states that an entity can hold are part of its structure, so the
model declares that they exist. But which state transitions are allowed, and
who may trigger them, is a prescriptive constraint — a rule. Thus, the model
defines the vocabulary of states, but business rules define the conditions under
which those states may transition from one to another.

== Glossary versus model

The glossary is separate from the model. The model defines entities, but not
every domain term is an entity. For example, _reservation_, _credential_, and
_currency_ are domain vocabulary with no structural definition.

The glossary is the flat index of _all_ domain vocabulary. For any term that
is also an entity, it gives a brief definition and links into the model for the
full structure.

== Journeys versus interfaces

Journeys define the user experience — wireframes for UI systems, annotated call
sequences for headless ones. Interfaces define the external contracts — the
operations, resources, and events the system exposes, described behaviorally.

For a UI product, interfaces may be thin and journeys rich. For a headless
system, the reverse.
