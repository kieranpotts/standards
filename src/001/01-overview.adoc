= Overview

A software requirements specification is a _living_ description of what the production system does today. It is most valuable when it is paired with a permanent, chronological record of the product decisions that shaped it — so that the current specification is always justified by the reasoning that produced it.

== A living specification

Most requirements documents rot over time. Written once at the start of a project, they are abandoned as the system evolves past them. Within months they describe a system that no longer exists, and stakeholder trust in the specification deteriorates in response.

A specification can avoid that fate by binding itself to production. The objective is for the specification artifacts to always describe how the system behaves for real users right now.

To achieve this, a change to the specification artifacts MUST NOT be released until the corresponding changes in code and configuration are themselves live in production.

The payoff is a single, trustworthy answer to "`what does the system do?`" New team members, auditors, support staff, and other stakeholders can read the software specification and have confidence that it is correct.

== A product decision log

A specification alone tells you _what_ the system does, but not _why_.

A good software requirements management workflow keeps a second artifact alongside the specification – a product decision log.

Every significant proposed change — whether ultimately implemented or rejected — SHOULD be preserved as a record of the decision and its rationale.

The product decision log is the institutional memory of the product. When someone asks "`why doesn't the catalog support multiple currencies?`" or "`why did we reject open, unauthenticated access?`", the answer is on record, with the reasoning intact.

== Separation of product and implementation

A software requirements specification SHOULD be agnostic of implementation. It records _what_ the system does and _why_, in the language of the business — but not _how_ it is built, beyond what is strictly necessary to understand the system's functional and non-functional requirements.

Technical decisions — about the technologies, tools, and architectural patterns used to construct, verify, and host the solution — SHOULD live separately. A request for comments (RFC) repository (see link:../003/README.adoc[*TS-3: Design Docs*]) is a useful companion to the SRS that serves this purpose.

Keeping the two apart means the specification survives re-platforming: rebuild the system on an entirely different stack and its SRS need not change. It also keeps each artifact aligned with its audience. Free of technical detail, the specification is more valuable to business and other non-technical stakeholders.

== SRS versus PRD

A software requirements specification (SRS) is distinct from a product requirements document (PRD), though there is much overlap between the two. Both describe a system from the user's perspective, and both stay light on implementation detail. What separates them is formality and completeness.

A PRD is an upstream artifact, owned by product management, that defines the problem in an informal format, plus desired outcomes and timelines for delivery. A PRD captures _what_ a product should do and _why_ it matters — the problem, the target users, the desired outcomes. It needs only enough detail to align stakeholders on broad goals and scope.

The SRS is the PRD's formal, testable successor. It turns the product vision, defined into the PRD, into a verifiable, testable specification – measurable acceptance criteria that development and test-case creation can be driven from directly. It reads less like a vision and more like a contract between the business and the technical teams.

Unlike the PRD, the SRS is maintained by technical stakeholders (though in collaboration with business stakeholders) and kept close to the code.

The PRD comes first, to define the problem. The SRS follows as its more refined, formal successor.

[cols="1,2,2"]
|===
| | PRD | SRS

| *Question answered*
| What should the product do, and why?
| What, precisely, does the system do?

| *Primary audience*
| Business stakeholders
| Engineers and testers

| *Author*
| Product managers
| Software architects and technical leads

| *Formality*
| Just enough to align on goals, scope, and priorities
| Detailed and testable

| *Typical contents*
| Problem statement, resource constraints, prioritization, roadmap, user personas
| Functional and non-functional requirements, user stories, success metrics and KPIs
|===

Both stay implementation-neutral, but the SRS may lean slightly closer to it. A good SRS models the domain, and that domain model becomes the foundation for the software architecture. It may also, where strictly necessary to state an acceptance criterion, touch on interfaces such as APIs.

This standard governs the *SRS* only. The PRD precedes it and is owned by product management; how a PRD is written and maintained is out of scope. TS-1 begins where the PRD leaves off — turning an agreed product vision into a precise, testable, maintained specification of the system.

== Why version control

Software requirements can be managed using alternative tools such as wikis and issue trackers, but these tend to be leakier than the code repository model. Wikis and static documents describe intent at a point in time but drift out of sync with the running system. Issue trackers are good for work-in-flight but poor as a durable record — closed tickets scatter, and the "`current truth`" is never assembled in one place.

Executable tests are a good complement: they carry behavior in a verifiable format. But while they verify behavior, they don't capture motivation, scope, or the alternatives considered.

It is RECOMMENDED to keep the specification under the same version control system used to manage the software itself, colocated with (or close to) the code it specifies. The repository model binds the specification to production so it stays accurate, keeps an ordered decision log rather than an opaque edit trail, and holds the prose context that executable tests cannot — all while adding minimal friction, because the specification lives where the work already happens.
