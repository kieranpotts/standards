= Best practices

Practical guidance for writing requirements and keeping a specification trustworthy.

== Specify the end state, not a changelog

A proposal's specification edits SHOULD describe the system as it will be _once the change has shipped_ — not the steps taken to get there. Write "`authenticated callers can filter the catalog by species,`" not "`we will add a species filter.`"

The diff against the current specification already shows what is changing. The prose should read as a description of the destination, so that when the proposal is released the specification is simply _true_. How the change is rolled out — migration steps, sequencing, feature flags — is an implementation concern and does not belong in the specification.

== Keep description and reasoning in their proper homes

The specification says _what_ the system does; the proposal says _why_ a change was made. Don't smuggle rationale into the specification — it is meant to read as a timeless description of the present. Likewise, don't restate the full specification in a proposal — link to the artifacts it edits.

The proposal is the place to be honest about motivation, alternatives considered, and trade-offs accepted. That honesty is what makes the decision log valuable years later.

== Record rejections as carefully as acceptances

A rejected proposal is not a failure to be hidden; it is a decision worth remembering. Reverting its specification edits leaves the system unchanged, but keeping the document means the next person with the same idea can read why it was not pursued. Write the motivation, alternatives, and trade-offs of a doomed proposal with the same care as a winning one.

== Write functional requirements as testable scenarios

Prefer <<_features, Gherkin>> scenarios for functional requirements: each is an acceptance criterion — a concrete, observable behavior checkable against the running system.

* Keep scenarios concrete. Prefer "`then the response contains at most 10 records`" over "`then a reasonable number of records is returned.`"
* Define one behavior per scenario. If a scenario has two unrelated `Then` outcomes, it is probably two scenarios.
* Use the project's <<_context, ubiquitous language>>. The same term should mean the same thing in the glossary, the model, and every scenario.
* Cover the unhappy paths too — empty results, not-found, unauthorized. The edge cases are where requirements are most often ambiguous.
* Lift cross-cutting invariants out of scenarios and into <<_behaviors, rules>>, then reference them.

== State qualities as measurable thresholds

A quality requirement that cannot be measured cannot be verified, and an unverifiable requirement is just a wish. Specify qualities as concrete, testable thresholds, ideally at a named percentile and load: "`list responses within 300 ms at the 95th percentile under normal load,`" not "`the API should be fast.`" Vague qualities give the false comfort of a requirement without the substance of one.

The qualities a specification states are its _dynamic_ ones — what the system must achieve at runtime, observable to users. Static qualities of the code and design (readability, modularity, and the like) are a design concern, not a requirement the specification states (see <<_qualities>>).

== Keep the specification honest

The specification's value rests entirely on one promise: that the main line describes production. Protect that promise. Do not merge an accepted proposal until its change is actually live, and reconcile any divergence discovered during implementation back into the specification before release.
