= TS-40: CSS
:toc: macro
:toc-title: Contents

CSS applies styles in a cascading fashion — an inheritance model that cannot be
turned off. In small codebases the cascade is a benefit. But in large,
long-running, multi-contributor projects it becomes a liability, tightly
coupling the presentation of every part of a webpage and making for a brittle
codebase.

Until recently, CSS had no native, universally supported mechanism for scoping
styles to a fragment of markup. That changed with the `@scope` at-rule, which
as of 2024 is supported by Chrome, Edge, Firefox, and Safari. The wider Web
Components platform also offers style encapsulation via the Shadow DOM API,
but that is not part of CSS itself.

In the absence of native scoping, web developers have long relied on
user-land conventions — BEM, SMACSS, OOCSS, CSS Modules, CSS-in-JS — to
impose the discipline that the cascade doesn't provide. This technical
standard builds on those class naming conventions to control the CSS cascade
in raw, native CSS code, with the aim of producing maintainable, scalable
interfaces regardless of whether stylesheets are hand-written, compiled from
a preprocessor like Sass or Less, or generated by a component framework.

Even with `@scope`, a well-defined CSS architecture remains useful. Besides
easier maintenance and extensibility, benefits include:

* Consistent naming and structure that reduce cognitive load when navigating
  an unfamiliar or long-running codebase.

* Predictable specificity, avoiding the need for `!important` or ever-deeper
  selector chains to override styles.

* Safer refactoring, since well-scoped rules can be changed or removed without
  unintended side effects elsewhere on the page.

* Reusable, composable building blocks — layouts, elements, widgets, and
  modifiers — that can be shared across teams and projects.

* A shared vocabulary that makes code reviews, onboarding, and collaboration
  between designers and developers more efficient.
