= TS-40: CSS
:toc: macro
:toc-title: Contents

CSS applies styles in a cascading fashion — an inheritance model that cannot be
turned off. In small codebases the cascade is a benefit. But in large,
long-running, multi-contributor projects it becomes a liability, because it
tightly couples the presentation of every part of a webpage, making for a
brittle codebase.

Until recently, CSS had no native, universally supported mechanism for scoping
styles to a fragment of markup. That changed with the introduction of the `@scope`
at-rule, which as of 2024 is supported by Chrome, Edge, Firefox, and Safari. The
wider Web Components platform also provides native style encapsulation via the
Shadow DOM API — but this is not implemented at the language level of CSS itself.

Historically web developers have had to impose their own discipline for building
modular, maintainable web interfaces. Techniques such as BEM, CSS Modules, and
CSS-in-JS have all offered alternative solutions to the same fundamental
problem of _how to control the CSS cascade_ to enable proper modularity in CSS
code.

This technical standard builds on user-land class naming conventions like BEM,
SMACSS, and OOCSS, to control the CSS cascade in raw, native CSS code.

The objective is to provide a set of guidelines that can be used to build
maintainable, scalable web interfaces in any context — whether CSS stylesheets
are written directly, or compiled from a preprocessor like Sass or Less, or even
generated from a higher abstraction such as JavaScript components.

Even with modern language extensions like `@scope`, it is still incredibly
useful to have a well-defined CSS architecture. Besides easier maintenance and
extensibility, benefits include:

* Consistent naming and structure that reduce cognitive load when navigating
  an unfamiliar or long-running codebase.

* Predictable specificity, avoiding the need for `!important` or ever-deeper
  selector chains to override styles.

* Safer refactoring, since well-scoped rules can be changed or removed without
  unintended side effects elsewhere on the page.

* Reusable, composable building blocks — layouts, elements, widgets, and
  modifiers — that can be shared across teams and projects.

* A shared vocabulary that makes code reviews, onboarding, and collaboration
  between designers and developers more efficient.

* Portability across tooling choices, since the same conventions apply
  whether CSS is authored by hand, compiled from a preprocessor, or generated
  by a component framework.

== References

* https://bradfrostweb.com/blog/post/atomic-web-design/[Atomic Design — Brad Frost]:
  A methodology for thinking about interfaces as a hierarchy of progressively
  more complex objects.

* https://bem.info[Block Element Modifier (BEM) — Yandex]:
  A widely adopted class naming convention.

* http://smacss.com[Scalable and Modular Architecture for CSS (SMACSS) — Jonathan Snook]:
  A style guide covering base, layout, module, state, and theme rules.

* https://suitcss.github.io[SUIT CSS — Nicolas Gallagher]:
  A class naming convention combined with extended CSS syntax.

* https://github.com/stubbornella/oocss[Object-Oriented CSS (OOCSS) — Nicole Sullivan]:
  One of the earliest widely adopted web design methodologies, published 2009.

* https://cssguidelin.es[CSS Guidelines — Harry Roberts]:
  A high-level advice document for writing sane, manageable CSS.

* https://google.github.io/styleguide/htmlcssguide.html[Google HTML/CSS Style Guide]:
  Formatting and naming conventions for HTML and CSS.
