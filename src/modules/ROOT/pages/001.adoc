This technical standard covers best practices for defining and managing software requirements.

[quote, Louis Srygley]
____
Without requirements or design, programming is the art of adding bugs to an
empty text file.
____

A *software requirements specification (SRS)*, also known as a *system requirements specification*, defines the
*acceptance criteria (ACs)* for a software system. It is the basis for the software's design, implementation, and
verification.

This technical standard covers two aspects of requirements specification.

1.  _What_ a good requirements specification looks like.

2.  _How_ a specification is managed over time so it stays an accurate, trusted description of the system as it actually
    is in production.

== References

* Brandolini, A (2013).
  {link-brandolini-2013-book}[_Introducing EventStorming_].
  Leanpub.
  — The origin of the event storming technique, first postulated in a
    {link-brandolini-2013-blog}[2013 blog post].

* Jacobson, I (1992).
  {link-jacobson-1992}[_Object-Oriented Software Engineering: A Use Case Driven Approach_].
  Addison-Wesley.
  — The book that introduced use case analysis.

* Cohn, M (2004).
  {link-cohn-2004-book}[_User Stories Applied: For Agile Software Development_].
  Addison-Wesley.
  — The standard treatment of user stories in requirements gathering. See also Cohn's blog posts
    {link-cohn-2004-blog-stories}[_User Stories and User Story Examples_]
    and {link-cohn-2004-blog-advantages}[_Advantages of User Stories for Requirements_].

* Patton, J.
  {link-patton-story-mapping}[_Story Mapping_].
  Jeff Patton & Associates.
  — The technique for arranging user stories into a two-dimensional map.

* Wynne, M (2015).
  {link-wynne-2015}[_Introducing Example Mapping_].
  Medium.
  — The card-based workshop technique for breaking a story into rules and examples.

* Adzic, G.
  {link-adzic-impact-mapping}[_Impact Mapping_].
  — The goal/actor/impact/deliverable framing for deciding what is worth building.

* Srivastava, PJ.
  {link-srivastava-short-guide}[_A Short Guide to Writing Software Requirements_].
  — Covers user stories, workflow diagrams, and the use of wireframes and visual diagrams.

* Wiegers, K (2022).
  {link-wiegers-2022}[_Plan for Tradeoffs: You Can't Optimize All Software Quality Attributes_].
  Stack Overflow.
  — Adapted from Wiegers' _Software Development Pearls_.
