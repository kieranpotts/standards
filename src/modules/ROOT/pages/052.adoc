= TS-52: Security and secrets management
:toc: macro
:toc-title: Contents

This technical standard covers security requirements for applications and best
practices for secrets management.

.TL;DR
****
* *Third-party code* – Must be reviewed for malicious patterns and run in an
  isolated environment (Docker, VM) before execution on a primary machine. This
  applies to open-source packages, AI-generated code, contractor deliverables,
  and recruitment coding challenges alike. Being rushed to execute unknown code
  is a red flag.
* *Encryption* – Data must be encrypted at rest and in transit.
* *Secrets* – Must not be hard-coded, committed to repositories, or sent to
  logs. Store primary secrets in dedicated secrets management systems (eg.
  HashiCorp Vault, AWS Secrets Manager). Rotate regularly; intervals should not
  exceed one week. Secrets must be narrowly-scoped to a single use case.
* *Compromised secrets* – Must be rotated immediately if leaked. Removing the
  secret from the environment where it was leaked is not sufficient.
* *Vulnerability scanning* – Source code must be scanned using SAST, DAST, and
  SCA tooling prior to release.
* *Threat modeling* – Should begin in the design phase and be treated as a
  living document, revised as the system evolves.
* *Authentication* – Token- or certificate-based authentication is preferred.
  Passwords must be strong, hashed, and salted (SHA-3/SHA-2). Re-authentication
  is required before destructive operations. Failed attempts must be limited and
  logged.
* *Authorization* – Least-privilege principle applies. Access must always be
  verified server-side before any operation is performed.
* *Network security* – Inbound and outbound traffic must be limited to what the
  application requires.
* *Web application security* – Required security headers include
  `Strict-Transport-Security`, `Content-Security-Policy`, `X-Frame-Options`, and
  `X-Content-Type-Options`. Sensitive forms must disable autocomplete. No
  hard-coded credentials in client-side code.
* *Memory safety* – Components that process untrusted input should be written
  in a memory-safe language. Where they are not, compiler and OS mitigations
  (ASLR, DEP, stack canaries) must be enabled on every released artifact, and
  sanitized builds and fuzzing must supplement the standard scanning tools. A
  mitigation raises the cost of an attack; it is never a fix for the defect.
****
