= TS-9: Version control
:toc: macro
:toc-title: Contents

This technical standard covers the use of version control systems (VCS), also
known as revision control, source control, or source code management (SCM)
systems.

This standard defines an opinionated workflow for shepherding the source code of
software systems through the lifecycle of development, testing, and release.
This workflow is rooted in the principles of continuous integration and
continuous delivery – pillars of modern software development practices.

== References

* Chacon, S; Straub, B.
  https://git-scm.com/book/en/v2/Distributed-Git-Distributed-Workflows[_Pro Git: Distributed Workflows_].
  — Describes three repository-topology patterns for distributed collaboration
  – centralized, integration-manager (fork-and-pull), and
  dictator-and-lieutenants (hierarchical, for very large projects) – which are
  a distinct concern from the branch-naming-and-merging strategies covered by
  the other references below.

* Hintjens, P (2016).
  https://rfc.zeromq.org/spec/42/[_The Collective Code Construction Contract (C4)_].
  — A formal specification, rather than a descriptive pattern, for fork-and-pull
  contribution: a single `main` branch with no topic branches, mandatory
  pull requests reviewed by maintainers, and a prescribed patch and commit
  message format.

* Microsoft (2022).
  https://learn.microsoft.com/en-us/devops/develop/how-microsoft-develops-devops[_How Microsoft Develops with DevOps_].
  — Describes the "Microsoft Release Flow": trunk-based development with
  short-lived topic branches merged into `main` via pull request, and periodic
  release branches cut from `main` that never merge back. Hotfixes are made in
  `main` first, then cherry-picked forward into affected release branches – the
  same fix-forward discipline this technical standard requires.

* Li, J (2019).
  https://shopify.engineering/successfully-merging-work-1000-developers[_Successfully Merging the Work of 1000+ Developers_].
  — A case study of merge-queue infrastructure at scale: pull requests are
  batched, tested against a "predictive branch" ahead of `master`, and merged
  automatically once checks pass, with tolerance thresholds to stop flaky tests
  from blocking the queue. Directly relevant to the merge-queue technique noted
  in *xref:009.adoc[]* for catching semantic conflicts before they reach
  the trunk.

* Driessen, V (2010).
  https://nvie.com/posts/a-successful-git-branching-model/[_A Successful Git Branching Model_ (GitFlow)].
  — This branching-and-merging strategy was designed for the intermittent
  release of versioned software. It is characterized by its two main branches,
  `master` and `develop`. GitFlow was not intended for continuously delivered,
  singly versioned software like web apps, though it has been widely adopted for
  that purpose.

* GitLab (2014).
  https://about.gitlab.com/2014/09/29/gitlab-flow/[_GitLab Flow_]. — This
  workflow offers a better template for the source code management of
  continuously delivered web-based software systems.

* GitLab.
  https://about.gitlab.com/topics/version-control/what-is-gitlab-flow/[_What is GitLab Flow?_].
  — GitLab's current explainer of the same workflow introduced in the 2014 post
  above, covering its integration with issue tracking and continuous delivery.

* Chacon, S (2011).
  https://scottchacon.com/2011/08/31/github-flow.html[_GitHub Flow_]. — A
  minimalist workflow, ideal for personal and small open source projects. It
  uses a single `main` branch, and feature branches are created for each new
  feature or bug fix.

* GitHub.
  https://docs.github.com/en/get-started/using-github/github-flow[_GitHub Flow_].
  — GitHub's current documentation of the same workflow described in Chacon's
  original post above.

* Atlassian.
  https://www.atlassian.com/blog/archives/simple-git-workflow-is-simple[_Simple Git Workflow_].
  — This uses feature branches but with the rebase strategy suggested for
  integrations back to the main branch. It also adds environment branches and
  release branches.

* Ruka, A (2017).
  https://www.endoflineblog.com/oneflow-a-git-branching-model-and-workflow[_OneFlow – a Git Branching Model and Workflow_].
  — A simplified alternative to GitFlow that uses a single eternal branch,
  replacing GitFlow's `develop`, `release`, and `hotfix` branches with
  short-lived support branches and Git tags.

* Spiewak, D.
  https://gist.github.com/djspiewak/9f2f91085607a4859a66[_Git DMZ Flow_]. — A
  workflow built around a single "demilitarized zone" integration branch that
  automatically validates changes via CI before they reach a pristine,
  always-deployable `master`.

* Ellerby, B (2020).
  https://medium.com/serverless-transformation/serverless-flow-a-ci-cd-branching-workflow-optimized-for-speed-and-quality-6b98c5a4e489[_Serverless Flow: A CI/CD Branching Workflow Optimized for Speed and Quality_].
  — A GitHub Flow variant for serverless architectures, using ephemeral
  per-branch environments to test changes in isolation before they reach
  production.

* Wilsenach, R (2021).
  https://martinfowler.com/articles/ship-show-ask.html[_Ship / Show / Ask_]. —
  A workflow that classifies each change by review posture – ship without
  review, show for asynchronous feedback after merging, or ask for review
  before merging – rather than applying the same review gate to every change.

* https://trunkbaseddevelopment.com/[_Trunk-Based Development_]. — This workflow
  utilizes a single branch called `trunk`, to which all developers continuously
  integrate their changes, while resisting the temptation to create any other
  long-lived branches.

* Atlassian.
  https://www.atlassian.com/git/tutorials/comparing-workflows[_Comparing Git Workflows_].
  — A good overview of the main design choices to be made when establishing a
  Git workflow.

* Precht, P.
  https://rebase-book.com/[_REBASE: The Complete Guide on Rebasing in Git_]. —
  A book-length treatment of rebasing mechanics, from simple and interactive
  rebasing to cherry-picking and practical workflows, complementing the
  rebase-up and merge-down sync strategies described in
  *xref:009.adoc[]*.

* https://git.kernel.org/pub/scm/git/git.git/tree/Documentation/SubmittingPatches?id=HEAD[_Submitting Patches_].
  — Guidelines for writing commit messages for patches to the Git project
  itself, and which form the basis for most commit conventions, including
  Conventional Commits.

* https://www.conventionalcommits.org/[_Conventional Commits_]. — A
  widely-adopted standard for writing commit messages, from which changelogs can
  be auto-generated.

* Angular.
  https://github.com/angular/angular/blob/22b96b9/CONTRIBUTING.md#-commit-message-guidelines[_Commit Message Guidelines_].
  — The inspiration for Conventional Commits.

* Wiggins, A (2017). https://12factor.net/[_The Twelve-Factor App_]. — Factor I
  (Codebase) states that a single codebase, tracked in version control, deploys
  to multiple environments, with one-to-one correspondence between codebase and
  app — directly relevant to the single-reference-repository and
  self-contained-repository principles in *xref:009.adoc[]*.
