= TS-2: Software architecture qualities
:toc: macro
:toc-title: Contents

This technical standard establishes nine core qualities for evaluating a
software system's design. In no particular order, these qualities are the
following.

1.  *Completeness.* +
    Whether a software system provides all the functions and behaviors its
    users need.

2.  *Correctness.* +
    A system's ability to maintain valid, consistent state.

3.  *Performance.* +
    How well a system operates within its specified constraints — latency,
    throughput, availability, security, and other dynamic quality attributes
    that are observed at runtime.

4.  *Reliability.* +
    A system's ability to handle and recover from failures of all kinds.

5.  *Experience.* +
    How a system is perceived by its users.

6.  *Habitability.* +
    How easy a system is for developers to maintain and evolve.

7.  *Cohesiveness.* +
    To what degree a system's design forms a unified, consistent whole.

8.  *Changeability.* +
    The ease with which software can be adapted to changing requirements.

9.  *Simplicity.* +
    How well a system minimizes unnecessary complexity in both its
    interface and implementation.

These software architecture qualities are universal. They have an impact at every
abstraction level within a solution's architecture, and they are relevant to all
types of software – whatever the runtime environment, whatever the programming
language, and whether the system is distributed or single-node.

No priority should be assumed from the order in which these qualities are
presented. Their relative importance will differ between business domains and
architectural styles. But _all_ these qualities are of importance in _every_
software system to some degree.

It's best not to view these qualities as being mutually exclusive. In fact,
there's much overlap between them and they reinforce one another. For example,
the design constraints necessary to make a system fast and responsive tend also
to result in system designs that are simple, easy to change, and fault-tolerant.

Taken as a whole, these quality attributes form a cohesive software design
philosophy.

Nevertheless, some trade-offs are involved where qualities compete with one
another for priority in the design. This is the subject of the final section
of this technical standard.

This technical standard also touches upon the software design _process_ itself.
Topics such as iterative and incremental development, feedback loops, and domain
modeling are mentioned. After all, these are important methods and tools to help
us achieve our design goals. But the focus of this technical standard is the end
result – what good software architecture looks like – not the means of getting
there.

Related standards include xref:005.adoc[*TS-5: Application architecture*], which
covers architectural patterns for single-node applications, and
xref:007.adoc[*TS-7: Code design*], which covers low-level concerns such as
code formatting and exception handling.
