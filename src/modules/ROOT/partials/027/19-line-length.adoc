[#line-length]
= Line length and wrapping

In CommonMark, a single newline inside a paragraph is a soft break, and it renders as a space. A paragraph split across several source lines therefore renders identically to the same paragraph written on one line. How prose is wrapped in the source is a therefore a decision about editing, and the presentation of diffs in code review, not about rendering.

There are three common approaches to wrapping prose in the source. Each has costs and benefits.

* *One line per paragraph.* Each paragraph is written on a single source line, however long, and the editor soft wraps it for display, eg. `"editor.wordWrap": "on"` in VS Code. This is the simplest approach. There is no reflow, and no wrap points break inline constructs like bold and italic text. It matches what most WYSIWYG-adjacent tools, such as note apps and Markdown exporters, produce. The downside is that one line is a whole paragraph, so a small word changes across multiple paragraphs can appear to impact a whole document. Word-level diffs (eg. `git diff --word-diff`) and the intra-line highlighting in code review tools take most of the sting out of this.

* *Fixed-width hard wrapping.* Lines are broken at a fixed column, usually 80, sometimes 72 or 100. This is the traditional approach. It reads well in a terminal or plain-text viewer, and it is the only sensible option where the consumer of the text cannot reflow it, such as commit messages and plain `.txt` files. The downside is that inserting a word near the top of a paragraph reflows every line below it, inflating diffs and manufacturing merge conflicts. Best done with a formatter that reflows automatically.

* *Semantic line breaks.* Lines are broken at sentence ends, and sometimes at clause boundaries, but never at an arbitrary column count. This is also called "ventilated prose" or, more simply, "one sentence per line". Brandon Rhodes popularised the approach in a 2012 essay, and https://sembr.org[sembr.org] is a loose specification. It gives the diff granularity of fixed-width wrapping without the reflow churn, because editing one sentence touches one line. Reviewers can comment on a specific sentence. It also makes over-long sentences visually obvious in the source. The downsides are that the raw files look odd to people who are not familiar with the convention, and those contributors soon reintroduce mixed styles.

This technical standard does not mandate one approach, it only defines the following ground rules.

* A repository SHOULD choose one approach for its Markdown content and record the choice where contributors will find it, such as its `CONTRIBUTING.md` file.

* Within a file, the chosen approach MUST be applied consistently. A file that mixes approaches has the costs of each and the benefits of none.

* When editing an existing file, follow the approach it already uses.

Wrapping applies to prose only. Fenced and indented code blocks keep the line structure their content needs, and code samples follow the line-length rules of the relevant language standard. The cells of a table row MUST sit in a single source line. And other Markdown constructs such as headings do not support multiline syntax.
