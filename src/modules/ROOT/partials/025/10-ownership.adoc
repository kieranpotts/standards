= Ownership and staleness

Documentation without an owner tends to rot silently, because no one notices
when it drifts from the system it describes and no one is accountable for fixing
it.

Reference documentation (READMEs, API docs, architecture docs) SHOULD be owned
by whoever owns the code it describes, and updated in the same change that
changes the described behavior. A pull request that changes an API's behavior
without updating its documentation SHOULD be treated as incomplete, in the same
way a pull request that changes behavior without updating its tests would be.

Where documentation cannot reasonably be kept current – because it describes a
system no one maintains, or a decision that predates the current team – mark it
explicitly as historical rather than leaving readers to guess.

Prefer documentation whose staleness is self-evident (generated from code, or
dated and clearly historical) over documentation whose staleness is silent
(hand-maintained prose with no indication of when it was last true).

== Reviewing documentation

A small set of fresh, accurate documentation is better than a sprawling,
loose assembly of documentation in various states of disrepair. Outdated
content SHOULD be deleted in small, regular increments, rather than left to
accumulate into a single overdue cleanup that never happens — the same
"delete rather than let it rot" discipline that applies to unused code.

Reviewing documentation is not the same discipline as reviewing code, and
applying code-review rigor to a documentation change tends to produce
exactly the sprawl this section warns against — every reviewer's stylistic
preference becomes a blocking comment, and nothing gets merged.

* A reviewer SHOULD approve a documentation change immediately where it is
  reasonable to do so, trusting that any remaining minor comments will be
  addressed, rather than blocking on them.
* A reviewer SHOULD suggest a specific alternative rather than leaving a
  vague comment, and SHOULD raise a substantial disagreement as their own
  follow-up change rather than blocking the change under review on it.
* An author SHOULD avoid spending review cycles on trivial argument, and
  SHOULD capitulate early on a stylistic disagreement rather than defend it
  at length — the cost of a slightly-worse phrasing is lower than the cost
  of a documentation change stalled in review.

This review-etiquette standard exists for the same reason as the
support-driven feedback loop in <<Support-driven documentation>>:
documentation that is easy to update stays current; documentation that is
expensive to update — because every change is litigated like a code
review — stops getting updated at all.
