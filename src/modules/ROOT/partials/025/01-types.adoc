= Types of documentation

Technical documentation takes numerous forms, each with a different audience, owner, lifecycle, and update trigger.

The different forms of technical documentation SHOULD be captured in distinct artifacts that are located separately from one another. Conflating multiple forms of documentation leads to verbose, complex docs with no clear ownership or maintenance lifecycle. Readers with different needs are poorly served by the same text, volatile content goes stale alongside stable content, and records that should be immutable get edited in place, losing the history of why things changed.

At a minimum, distinguish between the following types of documentation.

* *User documentation.* Describes how to use a software product. Kept strictly in-sync with new releases that change the public interface or other surface characteristics of the software. *Reference documentation* is one subset of user documentation, alongside installation and usage tutorials, and other guidance oriented around the user's tasks and goals.

* *Architecture and design documentation.* Explains how major components fit together. Updated when key building blocks, data flows, and deployment topologies change.

* *Process documentation.* Records point-in-time decisions. These docs are typically treated as immutable once written. Examples include ADRs, RFCs, and design docs.

* *Operational documentation.* Runbooks, incident playbooks, and deployment guides. Written for on-call engineers under time pressure. Scan-ability is prioritized over depth.

* *Onboarding documentation.* Oriented at newcomers who lack context that existing contributors take for granted. Higher tolerance for explaining "obvious" things.

* *Historical documentation.* Changelogs and release notes.
