= When not to document

Not everything needs a separate document. A document that merely restates what the code already makes obvious adds a
second thing to keep in sync for no reader benefit.

Before creating a new document, consider whether the same information would be better expressed as:

- Self-documenting code (clear naming, small functions, obvious structure) requiring no separate explanation.

- A code comment, if the context is local to a single function or module.

- A type signature or schema, if the information is structural (shape of data, valid states).

- A test, if the information is a worked example of expected behavior – tests are documentation that is verified to stay
  correct.

Create a standalone document when the information is broader than any single piece of code, needs to be read before the
code is (onboarding, architecture overview), or needs to persist independently of the current implementation (process
documentation, changelogs).

== The source-reading bias

The judgment above is usually made by whoever is closest to the code, and that is the person least likely to need the
document. An engineer who is fluent at reading unfamiliar source gets answers from the implementation, so a missing
document costs them very little. Engineers who are most comfortable reading unfamiliar codebases are therefore at risk
of habitually undervaluing documentation, and can be worse at documenting their own systems than the median engineer.

This is a property of teams rather than a failing of individuals. Reading source is a skill worth cultivating, and this
standard treats the source as the only authoritative account of how a system currently behaves (see
<<Process documentation>>). But that same fluency suppresses the signal that would otherwise expose a missing document.
The author never gets stuck, so nothing tells them that the explanation exists only in their own head, and the cost
lands instead on colleagues who read source more slowly, on operators who cannot read it at all, and on anyone whose
question arrives at three in the morning.

Treat "the code is self-documenting" as a claim to be tested, not one the author of that code can settle alone.

- *Let a reader make the call.* The test is whether someone who has not read the implementation can answer their
  question without reading it. Where that question is asked in code review, the answer SHOULD go into the documentation
  rather than into the review thread, where it is lost.

- *Have newcomers draft the onboarding material.* A newcomer can still see what is unexplained, and a maintainer has
  usually stopped being able to. Reviewing that material for accuracy is the maintainer's job. Writing it first SHOULD
  NOT be.

- *Treat a recurring question as a defect in the documentation.* The question is evidence that a reader could not get
  the answer from the source, whatever the person answering it would have done. See <<Support-driven documentation>>.

The enforcement point for all three is code review, per <<Ownership and staleness>>. A reviewer who could have answered
the question from the diff is not evidence that the document was unnecessary.
