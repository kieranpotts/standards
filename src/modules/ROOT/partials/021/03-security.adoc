= Security

Security measures MUST be implemented for both public and private APIs. Do not
assume that private/internal networks are secure.

All input MUST be validated and sanitized to prevent security vulnerabilities
such as SQL injection, cross-site scripting (XSS), and cross-site request
forgery (CSRF). Even if that input comes from another internal system that you
control and trust, you still MUST validate the input. Doing so reduces the
potential blast radius of security breaches in any one service.

An error response MUST NOT expose implementation details that could assist an
attacker, such as a stack trace, an internal file path, a database error
message, or the name and version of internal frameworks or libraries.
Attackers routinely use precisely this kind of accidental disclosure to
identify known vulnerabilities in a service's dependencies. Diagnostic detail
that would help a legitimate developer belongs in server-side logs, not in the
response body; see *Error handling* in *Payloads* for the corresponding
error-response rule.

Personally identifiable information (PII) MUST NOT be transmitted in a URL —
as a path segment or a query parameter value — since URLs are routinely
logged by proxies, load balancers, and browser history, in places the API
owner does not control and that are not designed to hold sensitive data. Where
an endpoint's semantics would otherwise require PII in the URL, pass it in the
request body or a header instead. See
xref:052.adoc[*TS-52: Security and secrets management*] and
xref:053.adoc[*TS-53: Privacy and data protection*] for the organization's
broader PII handling requirements, which this rule is a specific consequence
of.
