= Documentation and interface definition

HTTP APIs MUST be thoroughly documented.

An HTTP API's interface SHOULD be described using a machine-readable interface definition language (IDL), such as
https://www.openapis.org/[OpenAPI], rather than relying on prose documentation alone. A machine-readable contract
enables generated client SDKs, generated server-side request validation, and automated compatibility checking
against the versioning rules in *Versioning and managing breaking changes*.

== Design-first versus code-first

There are two common approaches to producing an API's interface definition, and an organization SHOULD pick one
deliberately rather than let it emerge by accident.

*Design-first.* The interface definition is authored before implementation begins, and both the producer and
consumer teams review and agree it as a contract. This gives early design feedback, establishes clear expectations
for both sides before code is written, and lets producer and consumer teams work in parallel – the consumer can
build against a mock generated from the contract while the producer implements it. It works best where the
interface is relatively stable once agreed; frequent requirement changes during development increase the overhead
of keeping the contract and the discussion around it up to date.

*Code-first.* The interface definition is generated from the implementation (eg. from code annotations), after or
alongside writing it. This allows rapid iteration, since there is no separate contract to keep synchronized while
requirements are still settling, and it is often more familiar to developers already comfortable with the
implementation language and framework. Its central risk is drift: a generated definition can silently fall out of
sync with the code's actual behavior across refactors, so automated checks comparing the generated definition
against actual API behavior are RECOMMENDED wherever this approach is used.

Whichever approach is used, the resulting interface definition SHOULD be committed to version control alongside the
API's implementation, so that its history can be reviewed the same way as code changes.
