= Releases

The release process — promoting stable code to production and delivering it to users — varies significantly depending on the context in which software is made and delivered. This standard accommodates that flexibility by decoupling the _development_ process from the _release_ process.

This standard REQUIRES continuous delivery, which means that every change is automatically built, tested, and prepared for release as part of the normal development workflow. However, continuous delivery does not mandate continuous _deployment_. You may choose to release small increments frequently, or to bundle multiple changes into infrequent release trains. The choice of release cadence is flexible, but the ability to release at any time is a core objective.

Every commit on `ready` is a candidate for release, but deployment is not mandatory — you choose the release strategy and cadence.

The choice of release *cadence* (big bang, release trains, or continuous deployment) and *rollout strategy* (rolling, canary, blue/green, feature flags) is covered in detail in xref:010.adoc[TS-10]. This section of TS-9 focuses on the version-control mechanics that support those choices.

== Release workflows

This technical standard RECOMMENDS a single release workflow, whatever the release cadence. A release is prepared in a *version commit* on `dev`, which flows through the trunk lines like any other commit. Once the version commit has passed quality assurance, the release is cut: the version commit is tagged, `ready` is fast-forwarded to the tag, and the `release` trunk is fast-forwarded to `ready`. Every commit and every version tag originates on the development trunk, and flows downstream toward the release trunk.

Release branches are a special case, for releases that carry artifacts of their own that must not flow back onto the trunk lines. They are described at the end of this section.

=== Version commits

Each release is prepared in a single `version` commit on the `dev` trunk, made directly or via a temporary branch. The version commit does two things.

* It promotes the changelog's `[Unreleased]` section to a heading for the new version and its release date, and starts a fresh, empty `[Unreleased]` section above it. The entries themselves are not written or edited here. They accumulate in the `[Unreleased]` section as changes land on `dev` (see xref:010.adoc[*TS-10: Releasing*]).
* It bumps the version string in any version manifests, eg. `package.json` or `pyproject.toml`.

The header carries the bare version number, with no `v` prefix: `version: 1.2.0`. The version number SHOULD be derived from the commits made since the pipeline's previous release tag, following the rules in xref:011.adoc[*TS-11: Versioning*].

Because the version commit is an ordinary commit on `dev`, release metadata lives on the trunk lines. Every trunk's changelog holds the full release history, and nothing ever needs to merge back from a release. Release preparation does NOT block ongoing development either: while the version commit makes its way through `test`, `dev` continues to receive commits for the release after that. *Release-time code freezes are not needed*. (Operational freezes for other reasons, such as high-traffic commercial events or holiday windows, are still appropriate; see xref:010.adoc[*TS-10: Releasing*].)

=== Release trunk

****
* Naming convention: `release`
* Lifespan: Permanent
* Protected: Yes
* Mutable: No
* Stable: Yes
* Requirement level: OPTIONAL
****

The `release` trunk marks the revision released to production. It has the same chronology of commits as the other trunk lines, but is usually some steps behind the tip of the `ready` trunk. Like `test` and `ready`, it only ever moves by fast-forward.

image::009/branches/parallel-trunks-with-release-trunk.svg[opts=inline]

The `release` trunk references compiled artifacts stored in an external artifact repository (registry, object storage, etc.), indexed by version tag or commit SHA. The key constraint: you must be able to deploy the latest revision _immediately_, without waiting for builds to complete or tests to rerun. This enables rapid incident response — for example, rolling back to a previous revision in production by redeploying an older build from the artifact repository.

=== Cutting a release

A release is cut once the version commit has passed quality assurance on `test`. The workflow follows these steps.

1. Tag the version commit with an annotated tag, signed where commit signing is in use: `git tag -a v<version> <commit>`.
2. Fast-forward `ready` to the tag: `git checkout ready && git merge --ff-only v<version>`. The `ready` trunk stops at the version commit, even where `test` has moved on. Later commits belong to the next release.
3. Fast-forward `release` to `ready`: `git checkout release && git merge --ff-only ready`.
4. Push the tag and the trunks: `git push origin v<version> ready release`. A plain `git push` does not transmit tags — annotated tags are local-only until pushed explicitly, whether by name (as here), with `git push --follow-tags` (pushes annotated tags reachable from the commits being pushed), or with `git push --tags` (pushes every tag in the local repository). Omitting the tag leaves the release tagged locally but absent from the remote, which breaks any automation or teammate workflow that resolves the release by tag.
5. Build and store compiled artifacts in an external artifact repository (container registry, package repository, object storage, etc.), indexed by the version tag.

The tag, `ready`, and `release` now mark the same commit. A pre-release, eg. `v1.3.0-rc.0`, is tagged the same way, but `ready` and `release` are left where they are, because a pre-release is not deployed to production.

If release preparation fails — for example, tests fail, an artifact build is broken, or the wrong version number is committed — fix forward. Commit the fix, or a corrected version commit, to `dev`, and let it flow through the pipeline again. Tags are permanent (see xref:011.adoc[*TS-11: Versioning*]), so a release that was tagged and then botched takes a new version number.

=== Release cadence

The same workflow serves every release cadence. For release trains and big bang releases, changes accumulate on `ready`, and a version commit is made whenever a release is due. For continuous deployment, the promotion of `release` to `ready` MAY be automated, so that every revision that passes verification on `ready` is deployed immediately, with its artifacts indexed by commit SHA. Versioned releases are then tagged on top of that flow, at whatever cadence suits the software's consumers.

=== Release branches

****
* Naming convention: `release/<version>`
* Lifespan: Temporary
* Protected: Yes
* Mutable: No
* Stable: Yes
* Requirement level: OPTIONAL
****

Release branches are a special case. They are for software in which each release carries *unique artifacts* — eg. release-specific configuration, feature flag states, or generated release notes that are true of that one release only. Committed to `dev`, such artifacts would flow downstream with every other commit, and carry over into every later release. A release branch keeps them off the mainline. Where a release has no artifacts of its own, use the release trunk workflow instead.

image::009/branches/parallel-trunks-with-release-branches.svg[opts=inline]

The release is still prepared in a version commit on `dev`, which reaches `ready` like any other commit. The release branch is cut from `ready` at the version commit, and named for the version, eg. `release/1.2.0`. If the version number is not yet decided when the branch is cut (for example, when QA findings may reclassify the release as major rather than minor), a placeholder name such as `release/next` MAY be used. The eventual tag carries the final version.

The release branch workflow follows these steps.

1. Fast-forward `ready` to the version commit: `git checkout ready && git merge --ff-only <commit>`.
2. Cut the release branch from `ready`: `git checkout -b release/<version> ready`.
3. Commit the release's unique artifacts to the release branch.
4. Tag the tip of the release branch with an annotated tag, signed where commit signing is in use: `git tag -a v<version>`. Push the tag explicitly: `git push origin v<version>`.
5. Build and store compiled artifacts in an external artifact repository, indexed by the version tag.
6. Delete the release branch: `git branch -D release/<version>` and `git push origin --delete release/<version>`. The version tag remains permanently in the repository, and keeps the release branch's commits reachable.

A release branch MUST contain only commits that add the release's unique artifacts. Code and configuration fixes MUST NOT be committed to a release branch. They flow through `dev` and `ready` like any other change. If release preparation fails, abandon the release branch, fix forward on `dev`, and cut a fresh release branch once the fix reaches `ready`.

A release branch SHOULD NOT be merged back into any trunk. Its artifacts belong to one release only, and merging them back would carry them into every later release, which is the very thing the release branch exists to prevent. Changes flow one way, from `dev` to the release branch, never the reverse. This is why the version commit, with its changelog and version manifest updates, is still made on `dev`: those changes do belong to every later release.

Because its version tag marks a commit that is not on the trunk lines, a release branch takes the place of the `release` trunk for that release: the `release` trunk cannot be fast-forwarded to the tag, and production is deployed from the tag instead. For the same reason, tools that find the previous release by walking a trunk's history, such as `git describe`, do not see tags on release branches.

== Artifact repositories

This standard distinguishes between two kinds of release artifacts.

* *Compiled artifacts* — Binaries, packages, container images, and other build outputs. These MUST NOT be stored in version control.

* *Release metadata* — Version tags, changelogs, release notes, configuration (secrets, feature flags). Version tags and changelogs are stored in version control, prepared in version commits and tags on the trunk lines. Release notes and release-specific configuration are typically managed outside the repository, eg. in the hosting provider's releases feature and in the deployment environment. Where they must be kept in version control, they go on release branches, so that they do not flow back onto the trunk lines.

Git is optimized for source code, not binaries. Storing compiled artifacts in Git repositories significantly slows clone operations, bloats the repository size, and complicates merges. For this reason, compiled artifacts MUST NOT be stored in version control.

Anti-patterns to avoid.

* *Git Large File System (LFS)* — While useful for source-controlled media (images, videos), it is not suitable for release artifacts. It still ties artifacts to the repository, slowing operations and complicating distribution.

* *Orphaned branches* — Using dedicated branches to store only build artifacts pollutes the repository history and does not solve the fundamental problems above.

Instead, store built artifacts in dedicated systems external to version control, eg..

* *Registries* — eg. Docker Hub, Amazon ECR, Maven Central, npm, PyPI, etc. — for containerized apps and libraries.

* xref:garden::object-storage.adoc[*Object storage*] — eg. Amazon S3, Google Cloud Storage, Azure Blob — for binaries, archives, and generic build outputs.

* *Generic artifact repositories* — eg. JFrog Artifactory, AWS CodeArtifact, Sonatype Nexus — for any artifact type.

Best practice is to create a two-way binding between version control and external artifact repositories using version numbering. For example, if `v1.2.3` is a tag in the repository, `v1.2.3` in the artifact repository refers to the compiled artifact built from the source code at the `v1.2.3` tag. This enables traceability and reproducible deployments.
