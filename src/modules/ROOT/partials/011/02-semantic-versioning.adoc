= Semantic versioning

It is RECOMMENDED to use the https://semver.org/[Semantic Versioning 2.0.0] scheme for versioning software components.
This is a widely adopted standard.

Semantic version numbers follow this format:
----
v{major}.{minor}.{patch}
----

* *<major>*: Increment this number by 1 when the release includes incompatible or breaking API changes. For user-facing
  GUIs, a breaking change could be considered to be a change in the behavior of an existing UI control, or removal of
  existing controls.

A breaking change is not limited to a change in the shape of a public API. It is any change that requires a consumer to
take action to avoid disruption to their own workflows — including a configuration change the consumer must make, or the
removal of a dependency the consumer's own tooling relied on, even where the programmatic contract is technically
unchanged. Framing "breaking" around required consumer action, rather than around the API surface alone, gives a usable
test for software where the "public API" is fuzzy or absent — end-user GUIs and CLIs, for example — where <<choosing-a-versioning-scheme,Choosing a versioning scheme>> already notes the surface area is hard to pin down.

* *<minor>*: Increment this number by 1 when the release includes user-facing changes that do not break backwards
  compatibility — new features, bug fixes, and runtime-quality improvements.

* *<patch>*: Increment this number by 1 when the release includes only internal changes that do not affect the
  user-visible contract — refactors, formatting changes, maintenance, and chores.

The following is a representative chronology of semantic version number progressions:

* `v1.0.0`
* `v1.1.0`
* `v1.2.0`
* `v1.2.1`
* `v2.0.0`
* `v2.0.1`
* `v2.0.2`
* `v2.1.0`

== Bumping versions from commit history

The mapping between SemVer increments and the commit conventions defined in xref:009.adoc[*TS-9*] is as
follows:

* Commits flagged `BREAKING` trigger a *major* bump.
* Commits of type `feature`, `fix`, or `runtime` (without `BREAKING`) trigger a *minor* bump. These are the user-facing
  changes that the version number communicates to consumers.
* Commits of type `refactor`, `format`, `maintenance`, or `chore` (without `BREAKING`) trigger a *patch* bump. These are
  internal changes that affect the codebase but not the user-visible contract.
* Commits flagged `INCOMPAT` (internal-only breaking changes) MUST NOT, on their own, trigger a major bump — they affect
  internal callers but not the public API contract, and so they bump patch like any other internal change.
* Commits of type `step`, `version`, `merge`, and `revert` are version-neutral; they do not trigger bumps.

When a release accumulates multiple commits, the highest applicable bump wins: BREAKING beats feature/fix/runtime beats
refactor/format/maintenance/chore.

Tools such as `semantic-release` and `release-please` can be configured to follow this mapping automatically. Manual
version selection MUST follow the same rules.

== Experimental features

Features that are clearly marked as "experimental", and that require users to explicitly opt-in to use them, MAY be
subsequently changed, modified significantly, or removed in a breaking way without triggering a major version bump. The
experimental status serves as an explicit contract that API stability is not guaranteed.

Experimental features MUST be documented as such, clearly visible to users who discover them, and their unstable status
MUST be communicated in release notes.

Once an experimental feature becomes stable and is no longer marked as experimental, the usual SemVer rules apply –
breaking changes to that feature then require a major version bump.

== Deprecation

Deprecation is a lifecycle stage, not a version-bump rule on its own — it is the announcement that a feature, endpoint,
or parameter will be removed in the future, followed by a notice period, followed by the removal itself. The two ends of
that lifecycle bump the version number differently:

* *Announcing* a deprecation is, on its own, a non-breaking change. Consumers are told a feature will go away, but
  nothing in their existing integration stops working yet. This triggers a *minor* bump, the same as any other
  user-facing, non-breaking change (see <<bumping-versions-from-commit-history,Bumping versions from commit history>>).

* *Removing* the deprecated feature is a breaking change once it lands, because it requires consumer action to avoid
  disruption. This triggers a *major* bump, following the same rule as any other breaking change, above.

Between those two events, the deprecated feature MUST continue to work exactly as before. Marking something deprecated
does not, on its own, license any change to its behavior — that would make the announcement itself a breaking change,
defeating the purpose of giving consumers notice.

The length of the notice period, the mechanism for warning consumers at runtime, and any approval process a deprecation
requires before it can proceed are release-governance concerns, not versioning-scheme concerns, and are outside this
standard's scope — see xref:010.adoc[*TS-10*]. Where the deprecated element is part of an HTTP API
specifically, the mechanics of annotating and signaling deprecated API elements are covered in
xref:021.adoc[*TS-21*].
