= Notations

The <<modeling-levels,modeling levels>> above describe _what_ to model. This section covers notations for _how_ to draw
the models.

== Unified Modeling Language (UML)

The https://www.omg.org/spec/UML/[Unified Modeling Language] (UML) is the best-known notation for modeling
object-oriented software systems. It is a graphical language for specifying, visualizing, and documenting the artifacts
of a system, standardized by the Object Management Group since 1997 as a unification of three earlier competing
notations (Booch, OMT, and OOSE).

UML diagrams fall into two broad categories:

* *Structure diagrams* depict the static elements of a system, irrespective of time — eg. class, component, package, and
  deployment diagrams.

* *Behavior diagrams* depict the dynamic interactions between elements of a system — eg. use case, sequence, activity,
  and state machine diagrams.

Of the many diagram types UML defines, *use case*, *class*, and *sequence* diagrams see the most real-world use. It is
NOT RECOMMENDED to attempt to learn or apply the full UML specification — only a small subset of it covers the majority
of practical modeling needs.

UML is most useful for modeling object-oriented designs, and is less suited to other programming paradigms, with the
notable exception of use case diagrams, which are paradigm-agnostic and useful for requirements analysis (see
xref:001.adoc[TS-1]).

UML diagrams serve two purposes, often over the same diagram's lifetime: *forward design*, sketching a system before it
is built, and *backward documentation*, describing a system as it was built. A diagram frequently starts as the former
and is fleshed out into the latter, accumulating implementation detail — field names, method signatures, concrete
relationships — as the design solidifies into code.

As with any notation, the goal is clear communication, not strict conformance to a specification. It is RECOMMENDED to
use only as much of UML's formal notation as is needed to convey a design clearly, deviating from the standard where
doing so improves clarity. UML diagrams SHOULD be drawn at a level of abstraction appropriate to their audience and
purpose — from rough whiteboard sketches during design, to detailed blueprints documenting an implementation.

See also xref:001.adoc[TS-1], a workshop-based technique for discovering the
domain events and components of a system, which is a useful precursor to formal modeling.

== Class diagram notation

A class diagram represents a class as a rectangle divided into three compartments: the class name, its attributes, and
its operations. Each member is prefixed with a visibility marker — `+` for public, `-` for private, `#` for protected,
`~` for package-private. An interface is drawn the same way, labeled with the `\<<interface>>` stereotype above its
name. An abstract class or operation is conventionally shown in _italics_; a `static` member is shown _underlined_.

Relationship lines connect classes, and the semantic distinctions between them are the part of the notation most often
confused:

* *Association.* A plain line. Denotes a general relationship where one class uses or knows about another, without
  implying ownership.

* *Aggregation.* A line with an unfilled diamond at the "whole" end. Denotes a "has-a" relationship where the part can
  exist independently of the whole — eg. a `Department` aggregates `Employee` objects that continue to exist if the
  department is dissolved.

* *Composition.* A line with a filled diamond at the "whole" end. Denotes a stronger "has-a" relationship where the
  part's lifecycle is bound to the whole — eg. an `Order` is composed of `OrderLine` objects that are deleted when the
  order is deleted. Composition is the relationship most often confused with aggregation; the deciding question is
  always whether the part can outlive the whole.

* *Generalization.* A line with an unfilled, triangular arrowhead pointing at the parent. Denotes inheritance — the
  "is-a" relationship between a subclass and its superclass, or between an implementing class and the interface it
  realizes.

* *Dependency.* A dashed line with an open arrowhead. Denotes that one class depends on another without holding a
  persistent reference to it — typically because it receives the other class as a method parameter, creates a local
  variable of that type, or calls one of its static methods.

A relationship MAY be reflexive — both ends of the line attach to the same class — to denote a self-referential
structure, eg. a `Node` that references other `Node` instances in a tree.

*Multiplicity* annotates each end of a relationship line with how many instances participate: `1` for exactly one,
`0..1` for zero or one, `*` (or `0..*`) for zero or more, and `1..*` for one or more. A `Person` with a one-to-many
association to `Address`, for example, is annotated `1` at the `Person` end and `1..*` (or `*`, if a person may have
none on file) at the `Address` end.

== Use case diagram notation

A use case diagram represents an actor — a user or external system — as a stick figure, and a use case as an oval
labeled with the goal it represents. A line connects an actor to each use case it participates in. Two relationships
extend this basic vocabulary: `\<<include>>`, a dashed arrow denoting that one use case always incorporates the behavior
of another, and `\<<extend>>`, a dashed arrow denoting that one use case optionally incorporates another's behavior
under some condition. Generalization — the same unfilled, triangular arrowhead used in class diagrams — denotes that one
actor or use case is a specialization of another.

This notation is distinct from the *use case analysis* technique covered in
xref:001.adoc[TS-1], which structures a use case's textual steps, preconditions,
and postconditions rather than its diagram.

== The model-code gap

A model that documents an existing system is only useful while it remains an accurate reflection of the code. Left
unmaintained, a model drifts from the system it describes — a discrepancy known as the *model-code gap* (see _"Just
Enough Software Architecture"_ by George Fairbanks). A model that is mostly accurate is one nobody can trust, since a
reader cannot tell which parts have drifted.

This risk applies to any model used as living documentation, not only formal design docs — see
xref:003.adoc[TS-3] for how the *living, decision-free* principle keeps a design doc synchronized with
production. Where a model is not maintained as living documentation — eg. a diagram drawn to support a one-time
discussion — it SHOULD be labeled as a point-in-time snapshot, so a future reader does not mistake it for current truth.
