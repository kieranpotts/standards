[#line-length]
= Line length and wrapping

Prose MUST NOT be "soft wrapped" — that is, continued on the next source line without any special line-break syntax. Each paragraph, list item, admonition, description-list entry, and table cell MUST be written on a single source line, however long that line is.

Asciidoctor combines the adjacent lines of a paragraph into a single line in the rendered output, so a soft wrap usually makes no difference to how a document renders. The risk is in the exceptions. A wrap that falls inside an inline construct — a bold or italic span, a link macro, an `xref:`, an inline passthrough — separates the markup from the text it applies to, and depending on the construct, it may silently fail to render. The wrap points also shift every time a sentence is edited, which invites exactly that kind of breakage when a paragraph is reflowed by hand or by a tool. Keeping each paragraph on one line removes the whole class of problem.

Visual wrapping is left to the editor. Authors SHOULD enable soft wrapping in their editor's display settings (eg. `"editor.wordWrap": "on"` in VS Code) rather than in the source text. Because a one-word edit changes a paragraph's whole line, reviewers SHOULD use a word-level diff (eg. `git diff --word-diff`) to read changes to prose.

Where a line break is needed in the rendered output, use a hard line break. See <<preserving-line-breaks,Preserving line breaks>>.

The rule applies to prose only. It does not apply to:

* *Verbatim content.* Source, listing, literal, and passthrough blocks, and verse blocks, keep the line structure their content needs. Code samples follow the line-length rules of the relevant language standard.

* *Hard line breaks.* A line that ends with a hard line break (a space followed by `+`) is intentional, and the text that follows it stays on its own line.

* *Table rows.* The cells of a table row MAY be written one per line. Each cell's content is itself prose, so it MUST NOT be soft wrapped.
