= Summary of requirements

This section lists the requirements that this technical standard states with MUST or MUST NOT, grouped by subject, each with a reference to the section that owns it. The owning section is normative and gives the reasoning. Where this summary and the owning section differ, the owning section prevails. Recommendations stated with SHOULD, RECOMMENDED, or MAY are not listed.

== Human oversight

* A human MUST be in the loop whenever AI tools are used for software development, maintenance, or operations (see <<human-in-the-loop,Human-in-the-loop>>).

* A model MUST NOT make the decisions that belong to a human (see <<when-not-to-use-ai,When not to use AI>>).

* Every change that an agent produces MUST have a named human owner (see <<team-policy,Team policy>>).

* All normal review and approval processes MUST remain in place for AI-generated code (see <<ai-assisted-workflows,AI-assisted development workflows>>).

* The developer who ran a session MUST read and understand every line before requesting review, and a second human MUST approve the change wherever peer review is required of human-written code (see <<reviewing-ai-authored-changes,Reviewing AI-authored changes>>).

== Verification

* Correctness MUST be established by a human or a deterministic check, and output MUST NOT be trusted on the model's confidence alone (see <<the-inherent-nature-of-the-technology,The inherent nature of the technology>> and <<hallucination>>).

* Agentic checks MUST NOT replace deterministic ones (see <<when-not-to-use-ai,When not to use AI>>).

* Exact computation MUST be delegated to a tool that executes it (see <<agentic-versus-automated,Agentic versus automated>>).

* Verification of AI-generated output MUST NOT rely solely on the session that produced it (see <<success-criteria,Success criteria>>).

* An agent that reviews output MUST NOT be the same agent, in the same session, that produced it (see <<sensors-in-the-pipeline,Sensors in the pipeline>> and <<graders,Graders>>).

* A backlog of success criteria MUST be treated as data the agent is graded against, not data it is trusted to maintain (see <<success-criteria,Success criteria>>).

* Inferential controls MUST NOT be the only line of defense where a deterministic alternative exists, and a human MUST review a sensor written by a model before it gates anything (see <<inferential-and-deterministic-controls,Inferential and deterministic controls>>).

* A blocking hook MUST return an error message specific enough for the agent to correct itself (see <<hooks-and-deterministic-enforcement,Hooks and deterministic enforcement>>).

== Workflows and loops

* The output of a pipeline step MUST be persisted to a durable store (see <<Persistence>>).

* Agents and scripts that operate on one repository at the same time MUST each have an isolated working copy (see <<isolated-environments,Isolated environments>>).

* A loop MUST separate the agent that produces work from the agent that judges it. The evaluator MUST be a separate session, MUST verify by execution, and MUST be anchored on deterministic gates (see <<loop-engineering,Loop engineering>>).

* A loop MUST have hard stops that do not depend on the model's cooperation, and its working state MUST live outside the conversation (see <<loop-engineering,Loop engineering>>).

== Prompts, context, and skills

* Prompts and reusable context MUST be token-efficient, and long prompts MUST be well structured (see <<prompt-engineering,Prompt engineering>> and <<reusable-context,Reusable context>>).

* The input parameters of a tool MUST be descriptive and unambiguous (see <<specialized-tools,Specialized tools>>).

* A cap on output tokens MUST be large enough to accommodate the expected output (see <<output-controls-and-determinism,Output controls and determinism>>).

* A `SKILL.md` file MUST contain YAML front-matter with a valid `name` and `description`, and MUST have an instructions section, a rules section, or both (see <<agent-skills,Agent skills>>).

* The location and naming of skills MUST be tailored to the harnesses in use, and a skill that is shared publicly MUST teach a pattern that transfers across projects (see <<agent-skills,Agent skills>>).

* The scripts bundled with a skill MUST take all input non-interactively and MUST handle edge cases gracefully (see <<progressive-disclosure,Progressive disclosure>>).

== Security

* Proprietary code and personal data MUST NOT be submitted to a model service that has not been approved for that class of data (see <<data-confidentiality,Data confidentiality>> and <<team-policy,Team policy>>).

* MCP servers and third-party skills MUST be treated as software dependencies, and a skill MUST NOT be granted tools that its stated purpose does not need (see <<treat-mcp-servers-as-dependencies,Treat MCP servers as dependencies>> and <<installing-third-party-skills,Installing third-party skills>>).

* A remote MCP server MUST authenticate its clients and MUST use encrypted transport, and an unauthenticated MCP server MUST NOT be exposed on a public network interface (see <<model-context-protocol,Model Context Protocol>>).

* A local model server that is bound to all interfaces MUST be protected by a firewall rule (see <<network-exposure,Network exposure>>).

* Credentials MUST NOT be committed in harness configuration (see <<harness-engineering,Harness engineering>>).

* An agent MUST NOT run with approval prompts disabled outside a sandbox in which at least one part of the lethal trifecta is absent by construction (see <<approval-modes,Approval modes>>).

* Authorization, verification, and approval MUST be enforced outside the model (see <<goals-without-judgment,Goals without judgment>>).

* Changes to a lockfile MUST be reviewed like any other change (see <<reviewing-agent-output,Reviewing agent output>>).

* The audit record of what an agent was asked and what it did MUST be engineered into a workflow (see <<costs-and-risks,Costs and risks>> and <<Auditability,Auditability>>).
