= Evaluation

xref:garden::ai-eval.adoc[*Evals*] (evaluations) are structured tests that measure how well an LLM, agent, skill, prompt, or AI-assisted or agentic workflow performs on a defined set of tasks. They are the AI equivalent of unit and regression tests, and they are widely cited as the most important — yet most often skipped — practice in building reliable AI systems.

In AI-assisted and agentic development, evals answer a question you can otherwise only guess at. Did a change to your model, prompt, skill, or harness improve outcomes, or quietly regress them?

Without evals, every such change is made blind.

== What to evaluate

Evals can be applied to any component of your AI setup, including.

* *Model selection.* <<benchmarks-and-leaderboards,Public benchmarks and leaderboards>> are a useful first filter, but they are no substitute for evaluating candidate models on your own representative tasks.

* *Context* (<<context-engineering,prompts>>, <<agent-skills,skills>>, and <<reusable-context,rules>>).

* *Harness configuration* (see <<harness-engineering,harness engineering>>), including available tools and guardrails.

* *Generated outputs.* The code, designs, or documentation your agents produce, judged against your acceptance criteria.

== Building an eval suite

A test case has three parts.

* a realistic input;
* a description of what success looks like;
* and any fixtures it needs.

Eval suites SHOULD live in version control alongside the code or prompts they exercise, so the two evolve together.

Start with a small suite covering your most common and most failure-prone cases, and grow it from real failures rather than speculation.

Beyond a handful of evals implemented as ad-hoc scripts, it is RECOMMENDED to use an established eval framework — such as https://github.com/openai/evals[OpenAI Evals], which pairs a runner with an open registry of reusable evals. For evaluating <<agent-skills,skills>>, Anthropic's https://github.com/anthropics/skills/tree/main/skills/skill-creator[`skill-creator`] skill automates much of the evaluation and iteration loop to refine the effectiveness of a new skill.

Keep some cases held out. A prompt, skill, or harness that is tuned against an eval suite comes to fit that suite, as a model overfits its training data. Reserve a set of cases that is never used while iterating, and run it only to confirm a result. If a tuned configuration improves on the working set but not on the held-out set, the improvement does not generalize.

[#graders]
== Graders

A grader is the part of an eval that decides whether an output passes. There are three kinds, and a suite usually mixes them.

* *Code-based graders* are deterministic checks, eg. string and regex matches, schema validation, a passing test suite, or a static analysis result. They are fast, cheap, and reproducible. Evals SHOULD use them for every property that can be verified mechanically.

* *Model-based graders* use an LLM as the judge, scoring an output against a rubric. They reach qualitative properties, such as clarity and tone, that code cannot check. Their verdicts are probabilistic, so they need calibrating. An evaluating model MUST be run in a session distinct from the one that generated the output being evaluated.

* *Human graders* are the reference against which the other two kinds are calibrated. They are slow and expensive, so use them to label a sample, not to grade every run.

Calibrate a model-based grader before trusting it. Have humans label a sample of outputs, run the grader over the same sample, and measure how often the two agree. Revise the rubric until the agreement is good enough for the decision the eval supports, and repeat the check whenever the grader's model or rubric changes. A rubric that asks for a pass or fail verdict on one specific criterion is easier to calibrate than one that asks for a score on a scale.

== Outcome and trajectory

An agent can be evaluated on its outcome, its trajectory, or both. The *outcome* is the final state of the environment, eg. whether the tests pass and the file is correct. The *trajectory* is the sequence of steps the agent took to get there, eg. which tools it called, in what order, and at what cost.

Grade the outcome first. An agent often reaches a correct result by a route its designer did not expect, and an eval that requires a particular sequence of tool calls fails valid solutions. Grade the trajectory only for properties that the outcome cannot show, eg. that the agent did not read a forbidden file, stayed within its tool quota, or asked for approval before a destructive action. Check the final state itself, not the agent's report of it.

== How to use evals

The central mechanism of evaluation is comparison. Run the same eval in two configurations — with and without a change, or against the previous version — and look at the delta in pass rate, latency, and token cost.

This tells you what the change buys against what it costs.

A change that improves none of pass rate, latency, or token cost is not earning its keep, whatever its other appeal. A change that holds the pass rate while cutting cost or latency does earn it; one that trades a lower pass rate for savings needs a deliberate decision.

Avoid over-specifying assertions up front. Instead, observe what the system produces, then write checks against those outputs.

== Sample size

Model output is <<output-controls-and-determinism,non-deterministic>>, so one run of one case is weak evidence. Run each case several times, assert against properties of the output instead of a single exact string, and report the pass rate across runs.

The number of cases and runs needed depends on the size of the difference to be detected. A large effect, eg. a change that moves the pass rate from 40% to 80%, shows in a few dozen runs. A difference of a few percentage points needs hundreds, and a comparison that rests on fewer is inside the noise. Run the baseline configuration twice to measure that noise before reading anything into a delta. Where a decision turns on a small difference, report a confidence interval with the pass rate.

== Running evals in CI

Evals SHOULD run automatically, not only when someone remembers to run them.

* Run a small, fast subset, weighted toward code-based graders, on every change to a prompt, skill, or harness configuration. Fail the build on a regression larger than the measured noise.

* Run the full suite on a schedule, and before adopting a new model or model version. A provider can change a model's behavior with no change on your side.

* Record the pass rate, latency, and token cost of every run with the commit that produced it, so that a regression can be traced to a change.

* Give the CI job its own budget cap and its own narrowly scoped credentials (see <<cost-optimization,cost optimization>> and <<secrets-in-context,Secrets in context>>).
