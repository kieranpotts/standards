= Accessibility testing

Accessibility testing verifies that the system is usable by people with disabilities, including visual, auditory, motor,
and cognitive impairments. Accessibility is both a legal requirement in many jurisdictions and a fundamental quality
attribute — a system that excludes a significant portion of its potential users is not fit for purpose.

Accessibility testing evaluates compliance with standards such as the
https://www.w3.org/WAI/standards-guidelines/wcag/[Web Content Accessibility Guidelines] (WCAG), Section 508 of the US
Rehabilitation Act, and the European Accessibility Act. These standards define specific, testable success criteria
across multiple conformance levels (A, AA, AAA), with Level AA being the most widely adopted target.

Accessibility cannot be fully evaluated by automated tools alone. Automated scanners can detect many common issues —
missing alternative text, insufficient color contrast, missing form labels, incorrect heading hierarchy — but they
cannot evaluate the actual experience of using the system with assistive technology. A page may pass every automated
check and still be unusable for a screen reader user if the reading order is illogical, interactive elements are poorly
labeled, or focus management is broken.

Accessibility testing should address multiple categories of impairment:

* *Visual impairments* — test with screen readers (eg. NVDA, JAWS, VoiceOver), screen magnifiers, and high-contrast
  modes. Verify that all content and functionality is available without visual perception.

* *Motor impairments* — test all functionality using keyboard-only navigation. Verify that focus order is logical, that
  all interactive elements are reachable, and that there are no keyboard traps.

* *Auditory impairments* — verify that audio content has captions or transcripts, and that information conveyed through
  sound is also conveyed visually.

* *Cognitive impairments* — evaluate the clarity of language, consistency of navigation, predictability of interactions,
  and availability of error prevention and recovery mechanisms.

Best practices:

* Test with real assistive technologies — screen readers, keyboard-only navigation, voice control, and screen magnifiers
  — not just automated scanning tools.

* Automated accessibility scanners are a valuable first pass and should be integrated into the CI/CD pipeline, but
  manual testing with assistive devices is essential for evaluating the actual user experience.

* Include users with disabilities in usability testing where possible. No amount of expert evaluation is a substitute
  for real user feedback.

* Address accessibility from the start of the design process. Retrofitting accessibility into an existing system is
  significantly more expensive than building it in from the beginning.

* Establish a target conformance level (eg. WCAG 2.1 Level AA) and treat failures against that level as defects that
  block release.

* Test across multiple assistive technology and browser combinations. Screen reader behavior varies significantly across
  platforms.

* Document accessibility requirements and test results as part of the standard quality assurance process, not as a
  separate activity.

== Automated accessibility testing in CI

Automated accessibility scanning MUST run in the continuous integration pipeline, not only as a manual, occasional
check. A scanner such as https://www.axe-core.org/[Axe] catches a bounded but useful subset of WCAG success criteria
automatically — missing `alt` attributes, unlabeled form inputs, insufficient color contrast, incorrect heading
hierarchy, missing landmarks — and it catches them on every change, before a regression reaches a human reviewer.

* Run the scanner on every merge request into the team's integration branch, so a regression is caught before it merges,
  not after release.

* Treat a subset of WCAG success criteria as fully automatable — for example, presence of `alt` attributes, form input
  labeling, page language identification, and heading/landmark structure — and treat the rest as requiring the manual
  coverage in <<Assistive technology test matrix and audit process>>. An automated scan is a floor, not a substitute for
  the full conformance check.

* Fail the build on a new violation, so accessibility regressions are treated the same as any other broken test, not
  routed around as a separate, lower-priority backlog.

* Re-run the full manual audit (see below) at a regular cadence regardless of CI status. Passing automated scans is
  necessary but not sufficient for conformance — a scanner cannot evaluate reading order, focus management, or the
  coherence of the experience with assistive technology.

== Assistive technology test matrix and audit process

Automated scanning and ad hoc manual checks are not sufficient on their own. A full accessibility audit exercises the
system with real assistive technologies, across a defined test matrix, on a recurring cadence rather than only before a
release.

* Maintain a documented test matrix naming the assistive technologies audits MUST cover — for example, a screen reader
  on each major platform (eg. JAWS and NVDA on Windows, VoiceOver on macOS/iOS), a screen magnifier, and a
  speech-recognition tool (eg. Dragon NaturallySpeaking). Screen reader behavior varies significantly across platforms
  and browser pairings, so the matrix MUST specify browser/assistive-technology combinations, not just the assistive
  technology alone.

* For each combination in the matrix, verify that all information is accessible and easy to understand, and that all
  functionality is accessible, easy to understand, and operable — not only that individual elements carry the correct
  markup.

* Test with default assistive-technology settings before testing with any customization, since default settings reflect
  what most users actually encounter.

* Schedule audits at a regular cadence, and additionally whenever a sprint introduces a major new feature or a
  significant change to an existing one. Do not defer the first accessibility check to the end of an iteration;
  requirements should be scoped for accessibility from the start, per <<Shift left>>.

* Where possible, include people who use assistive technology day-to-day in the audit, rather than relying only on
  testers simulating an impairment. Lived experience surfaces problems that a scripted walk-through misses.

* Record the matrix coverage and the audit's findings alongside other quality assurance results, so an audit's outcome
  is traceable in the same place as functional test results, not siloed in a separate report.
